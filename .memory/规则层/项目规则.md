## 📖 使用说明

本文档定义项目的强制规则，AI在**所有模式**（研究、创新、计划、执行、审查）都必须严格遵守。

**规则级别**：
- `[强制]`：必须遵守，违反将导致审查失败
- `[推荐]`：建议遵守，但可根据情况调整
- `[参考]`：可选遵守，作为最佳实践参考

   - 必须读取：项目规则.md、编码规范.md、数据库规范.md

## 1. 数据库规则

> **详细规范**：详见 `.memory/规则层/数据库规范.md`

### [强制] 配置管理
- 数据库配置严格限制在 `configs/database.yaml` 文件中
- **禁止**使用环境变量覆盖数据库配置
- **禁止**在代码中硬编码数据库连接信息
- 连接池配置：min_size=1, max_size=10

### [强制] 连接管理
- 必须使用连接池（psycopg3连接池）
- 必须使用上下文管理器（with语句）
- 禁止直接创建数据库连接
- 所有连接操作必须设置超时

### [强制] Schema分层架构
项目使用多Schema分层架构，不同Schema承担不同职责：
- **api** schema：数据操作接口（存储过程）
- **reporting** schema：报表查询（物化视图、查询函数）
- **monitoring** schema：性能监控
- **public** schema：核心数据（事实表、维度表）

### [强制] 数据操作规范
- 所有数据表的CRUD操作必须通过 `api` schema 的存储过程
- **禁止**在应用代码中直接写SQL的INSERT/UPDATE/DELETE
- 查询操作优先使用 `reporting` schema 的物化视图或函数
- 明细查询可直接查询 `public` schema 的表

### [强制] SQL编写规范
- **禁止字符串拼接SQL**：必须使用参数化查询
- **防止SQL注入**：所有用户输入必须使用占位符（%s）
- **查询超时**：所有查询必须设置超时时间
- **时间范围过滤**：时序数据查询必须包含时间范围

### [强制] 存储过程管理
- 所有存储过程必须记录在 `.memory/数据层/存储过程清单.md` 文档中
- 新增存储过程后必须立即更新存储过程清单文档
- 存储过程清单必须包含：
  - 完整的函数签名（包含参数类型和返回值类型）
  - 详细的用途说明
  - 可执行的使用示例
  - 所属Schema（api、public、reporting）
- 修改存储过程后必须同步更新文档
- **禁止**删除或修改存储过程而不更新文档

### [强制] 命名规范
- **表名**：小写+下划线，复数形式（如 fact_measurements）
- **前缀**：fact_（事实表）、dim_（维度表）、staging_（暂存表）、mv_（物化视图）
- **列名**：小写+下划线（如 device_id、ts_bucket）
- **函数名**：fn_前缀 + 小写+下划线（如 fn_training_timeseries_1s）
- **参数名**：p_前缀 + 小写+下划线（如 p_device_id）

### [强制] 注释规范
- 所有表必须有注释（COMMENT ON TABLE）
- 关键列必须有注释（COMMENT ON COLUMN）
- 所有函数必须有注释（COMMENT ON FUNCTION，使用$DOC$标记）
- 所有视图必须有注释（COMMENT ON VIEW，使用$DOC$标记）
- 注释必须使用中文
- 注释必须包含：用途、参数、返回值、示例

### [强制] TimescaleDB使用
- 时序数据必须使用TimescaleDB的Hypertable
- fact_measurements表：时间分区（ts_bucket）+ 空间分区（device_id，8个分区）
- 所有查询必须包含时间范围过滤
- 利用分区裁剪优化查询性能

### [强制] 事务处理
- 必须使用事务上下文管理器
- 事务尽可能短，减少锁持有时间
- 异常时必须回滚事务
- 默认隔离级别：READ COMMITTED

### [推荐] 性能优化
- 聚合查询优先使用物化视图（mv_measurements_hourly、mv_measurements_daily）
- 使用reporting.get_metrics_auto_multi自动选择粒度
- 索引覆盖常用查询字段
- 定期执行ANALYZE更新统计信息

## 2. 代码规范

> **详细规范**：详见 `.memory/规则层/编码规范.md`

### [强制] 文件大小限制
- 单文件代码行数不超过 **600行**（不包含注释和空行）
- 超过限制必须拆分为多个文件
- 检查方法：使用工具统计代码行数

### [强制] 设计原则
必须严格遵循**六大面向对象设计原则**（SOLID + LoD）：
1. **SRP** - 单一职责原则：一个类只负责一个功能领域
2. **OCP** - 开闭原则：对扩展开放，对修改封闭
3. **LSP** - 里氏替换原则：子类可以替换父类
4. **ISP** - 接口隔离原则：接口应该小而专注
5. **DIP** - 依赖倒置原则：依赖抽象而非具体实现
6. **LoD** - 迪米特法则：最少知识原则

### [强制] 语言和注释
- 所有代码注释必须使用**中文**
- 所有日志输出必须使用**中文**
- 所有错误消息必须使用**中文**
- 禁止中英文混杂

### [强制] 代码完整性
- **禁止**使用代码占位符（TODO、FIXME、...）除非在计划中明确说明
- **禁止**跳过或简化代码部分
- **禁止**使用省略号（...）作为代码占位符
- 所有函数必须包含完整的错误处理

### [强制] 命名规范
- **Python**：
  - 函数和变量：snake_case
  - 类：PascalCase
  - 常量：UPPER_SNAKE_CASE
  - 私有成员：_前缀
- **数据库**：
  - 表名：snake_case（复数形式）
  - 列名：snake_case
  - 函数名：fn_前缀 + snake_case
  - 参数名：p_前缀 + snake_case

### [强制] 日志规范
- 必须使用项目日志系统（app/core/logging/setup.py）
- 必须使用日志API：log_activity、log_sql、log_db_function、log_db_view、log_biz
- 必须包含上下文字段：request_id、trace_id、span_id等
- 必须脱敏敏感信息（密码、密钥、身份证号等）
- 日志格式：管道分隔（pipe）+ extra_json

### [强制] 错误处理
- 必须捕获具体异常，禁止裸except
- 必须记录错误日志
- 必须清理资源（使用with语句或try-finally）
- 异常消息必须使用中文

### [推荐] 代码格式
- 使用black格式化代码
- 使用isort排序导入
- 行长度不超过100字符
- 使用4空格缩进

## 3. 质量标准

> **详细标准**：详见 `.memory/规则层/质量标准.md`

### [强制] 代码质量指标
- **圈复杂度**：单个函数不超过 **10**（建议 ≤ 6）
- **函数长度**：不超过 **50行**（不含注释和空行）
- **参数数量**：不超过 **5个**（超过则使用对象封装）
- **代码覆盖率**：单元测试覆盖率 ≥ **80%**

### [强制] 错误处理
- 所有API接口必须包含try-except错误处理
- 所有数据库操作必须包含事务管理
- 所有外部调用必须包含超时和重试机制
- 异常必须记录日志

### [强制] 测试要求
- 新功能必须包含单元测试
- 关键业务逻辑必须包含集成测试
- 测试覆盖率不低于 **80%**
- 测试命名：`test_函数名_场景_期望结果`
- 必须测试：正常流程、边界条件、异常情况

### [强制] 文档要求
- 所有公共API必须包含docstring（Google风格）
- docstring必须包含：功能描述、参数说明、返回值说明、异常说明、使用示例
- API接口必须包含OpenAPI文档
- 数据库函数必须包含注释说明（使用COMMENT ON）

### [强制] 代码审查
- 所有代码必须经过至少1人审查
- 关键代码必须经过2人审查
- 审查意见必须全部解决才能合并
- 必须检查：编码规范、功能正确性、测试覆盖、性能、安全性、文档完整性

### [强制] 性能标准
- API接口响应时间：P95 < 1秒，P99 < 3秒
- 数据库查询：P95 < 2秒，P99 < 5秒
- 批量操作：< 10秒（P95），< 30秒（P99）

### [推荐] 质量检查工具
- **Linter**：pylint、ruff、mypy
- **格式化**：black、isort
- **测试**：pytest、pytest-cov
- **安全**：bandit

## 4. 架构约束

### [强制] 依赖管理
- 新增依赖必须使用包管理器（pip install、poetry add等）
- **禁止**手动编辑 requirements.txt、package.json
- 依赖版本必须锁定（使用 requirements.lock 或 poetry.lock）
- 安装依赖前必须征得用户同意

### [强制] 模块边界
- **适配器层**（app/adapters/）：数据库、文件系统、外部API访问
- **服务层**（app/services/）：业务逻辑
- **API层**（app/api/）：路由和请求处理
- **核心层**（app/core/）：配置、日志、工具
- **模型层**（app/models/）：数据模型

**分层规则**：
- 业务逻辑不能直接访问数据库（必须通过适配器层）
- API路由只能调用服务层，不能包含业务逻辑
- 跨层访问必须通过网关/适配器
- 禁止循环依赖

### [强制] 配置管理
- 所有配置必须在 `configs/` 目录
- 配置文件格式：YAML
- 配置优先级：CLI > ENV > YAML > 默认值
- **例外**：数据库配置仅支持YAML，禁止环境变量覆盖

**配置文件清单**：
- `configs/database.yaml` - 数据库配置
- `configs/logging.yaml` - 日志配置
- `configs/web.yaml` - Web服务配置
- `configs/ingest.yaml` - 数据导入配置
- `configs/system.yaml` - 系统配置

### [强制] 目录结构
- **禁止**访问 venv/、.venv/、env/、data/ 目录
- **禁止**修改 .git/ 目录
- 代码必须放在正确的目录下
- 配置必须放在 configs/ 目录
- 文档必须放在 docs/ 目录
- 脚本必须放在 scripts/ 目录

## 5. 安全规范

### [强制] 数据安全
- **禁止**在日志中输出敏感信息（密码、密钥、身份证号、手机号等）
- **禁止**在代码中硬编码密钥或密码
- 所有敏感配置必须使用环境变量或密钥管理服务
- 日志必须脱敏（使用logging.yaml中的mask_keys配置）

### [强制] 输入验证
- 所有用户输入必须进行验证和清理
- 所有SQL查询必须使用参数化查询，防止SQL注入
- 所有文件上传必须验证文件类型和大小
- 所有API参数必须使用Pydantic模型验证

### [强制] SQL安全
- **禁止**字符串拼接SQL
- 必须使用占位符（%s）
- 必须使用参数化查询
- 禁止动态构建表名或列名（如必须，需白名单验证）

### [强制] 权限管理
- 应用账号只授予必要权限（最小权限原则）
- 禁止使用超级用户连接数据库
- 密码必须加密存储

### [推荐] 安全检查工具
- 使用bandit进行安全检查
- 定期更新依赖，修复安全漏洞
- 使用pip-audit检查依赖漏洞

## 6. 性能要求

### [强制] 响应时间标准
| 类型 | P95 | P99 | 说明 |
|------|-----|-----|------|
| API接口 | < 1秒 | < 3秒 | 普通查询接口 |
| 数据库查询 | < 2秒 | < 5秒 | 单次查询 |
| 页面加载 | < 2秒 | < 4秒 | 首屏加载 |
| 批量操作 | < 10秒 | < 30秒 | 批量导入/导出 |

### [强制] 查询优化
- 时序数据查询必须包含时间范围过滤
- 大结果集必须分页（LIMIT + OFFSET）
- 避免SELECT *，明确指定需要的列
- 利用索引覆盖查询

### [推荐] 资源使用
- CPU使用率：< 70%（平均）
- 内存使用率：< 80%（平均）
- 数据库连接数：< 最大连接数的60%
- 单次查询返回数据不超过10000条

### [推荐] 性能监控
- 使用log_sql记录所有SQL执行时间
- 慢查询阈值：1000ms（配置在logging.yaml）
- 定期分析慢查询日志
- 使用EXPLAIN分析查询计划

## 10. MCP 工具使用要求

> 适用于本项目中 AI 使用的所有工具（Model Context Protocol 统一称为“MCP 工具”）。以下条款为[强制]，除非特别标注为[推荐]或[参考]。

### 10.1 工具选择矩阵 [强制]
- view：
  - 用途：读取具体文件/目录；精确查看函数/类/常量；用 `search_query_regex` 查找定义/引用。
  - 何时用：已知路径或需要定位精确行时。
- codebase-retrieval：
  - 用途：不知道文件位置时的高层检索；获取实现分布与概要。
  - 何时用：提出“Where is/Which file handles …”类问题时。
- git-commit-retrieval：
  - 用途：回溯历史实现、相似改动、变更动机与上下文。
  - 何时用：需要借鉴既有变更方式/理由时。
- str-replace-editor：
  - 用途：修改现有文件（单次修改≤150行）。
  - 规则：
    1) 修改前必须用 view 确认目标代码存在与上下文；
    2) 同一文件的多处修改尽量在一次调用内完成；
    3) 禁止整文件重写；
    4) 仅在必要范围内最小修改。
- save-file：
  - 用途：仅用于创建新文件（单文件≤300行）。
  - 禁止：用其覆盖已存在文件。
- launch-process / read-process / list-processes：
  - 用途：运行命令行（短任务 wait=true；长任务 wait=false 并监控）。
  - 规则：输出需记录命令、cwd、exit code 与关键信息行；禁止运行具有破坏性或未经授权的命令。
- web-search / web-fetch（只读）：
  - 用途：外部资料检索与抓取；优先官方文档；引用需注明来源。
- TaskManager（request_planning/get_next_task/...）：
  - 用途：多步骤或跨文件变更的任务编排；每步完成后需用户审批再继续。
- grep-search / view(search_query_regex)：
  - 用途：仓库内快速精确匹配与定位。

### 10.2 并行与效率 [强制]
- 默认并行：多个彼此独立的只读检索（view、codebase-retrieval、git-commit-retrieval、web-search）必须并行调用。
- 串行例外：仅在后续调用依赖前置结果时串行。
- 多文件独立编辑可并行；同一文件的编辑必须合并或顺序执行，避免冲突。

### 10.3 安全与权限边界 [强制]
- 需要明确用户许可：依赖安装、部署、外部系统写操作、可能产生费用的调用、修改数据库/生产数据。
- 允许的“安全验证”（无需额外许可）：运行测试/linters/类型检查/本地构建等不改动持久数据的操作。
- 运行命令时应验证成功标准：exit code==0 且日志无明显错误；失败需最小化修复后重试或请求用户指示。

### 10.4 编辑前验证与最小变更 [强制]
- 编辑前：用 view 确认目标函数/类/常量/文件存在与签名/结构；必要时用搜索确认影响面。
- 变更最小化：只改与需求直接相关的代码/文档；避免无关改动。
- 原子提交：将单一意图的修改集中为一次小而可审的变更；>150行需分批次执行。

### 10.5 展示与输出格式 [强制]
- 向用户展示多行代码时，必须使用 `<augment_code_snippet mode="EXCERPT" path="...">` XML 包裹，内部用四反引号并注明语言，展示不超过10行。
- 仅一行的标识符或表达式使用行内反引号。

### 10.6 任务清单与审批流程 [强制]
- 触发条件：多文件/跨层改动；预计>2次“编辑-验证”或>5次信息检索迭代；用户要求展示计划/进度。
- 流程约束：
  1) 创建请求与任务清单；
  2) 完成单个任务后，必须等待用户 `approve_task_completion`；
  3) 全部任务完成后，等待用户 `approve_request_completion` 再结束。

### 10.7 包管理 [强制]
- 必须使用包管理器命令（npm/pnpm/yarn、pip/poetry、cargo、go、composer、dotnet、mvn/gradle 等）进行依赖变更；禁止手动编辑依赖文件（除非进行无法通过命令完成的配置变更）。
- 运行安装/升级命令前必须取得用户明确许可。

### 10.8 禁止事项 [强制]
- 跳过用户审批继续执行下一任务。
- 覆盖重写整个文件或大范围无依据重构。
- 未经验证即编辑或批量替换。
- 重复打开相同 URL 或无意义的多轮检索。
- 执行具有破坏性或高风险命令（删除/写入生产数据、推送代码、合并分支等）。

### 10.9 MCP 自检清单 [强制]
- [ ] 选择了正确的工具（符合用途/范围）？
- [ ] 能并行的调用是否已并行？
- [ ] 是否遵守权限边界（需要许可的操作已征得同意）？
- [ ] 编辑前是否已用 view/搜索验证上下文与签名？
- [ ] 单次编辑是否 ≤150 行；新文件是否 ≤300 行？
- [ ] 是否在需要时使用了任务清单并遵循审批流程？
- [ ] 展示的代码是否按 augment_code_snippet 规范输出？


### 10.10 已安装 MCP 工具最佳实践与编排 [强制]

> 适配当前已安装的 MCP 工具：Sequential thinking、Context 7、PostgreSQL、Time、TaskManager、Memory。

#### 10.10.1 Sequential thinking（顺序思考引擎）
- 用途：复杂任务的分步推理、方案比较、假设-验证循环、纠错与回溯。
- 使用原则：
  - 仅作内部推理组织，不向用户泄露“思维过程”细节；对外仅给出结论与必要的精炼理由。
  - 在关键节点生成“解决方案假设”，随后以验证步骤（代码/测试/文档/查询）校验；失败则回溯修正。
  - 可动态调整 total_thoughts；当达到满意结论，将 `nextThoughtNeeded=false` 收敛。
- 典型场景：
  - 多文件改动的实施顺序规划
  - 不确定路径下的探索-验证-修正闭环

#### 10.10.2 Context 7（外部库文档检索）
- 组成：`resolve-library-id` → `get-library-docs`（必须先 resolve 再 get）。
- 选择规则：
  - 优先名称精确匹配；综合描述相关性、Snippet覆盖度、信任评分（7–10优先）。
  - 多个候选时，选择最相关者并在输出中简述理由；若歧义大，先向用户澄清。
- 使用要点：
  - `get-library-docs` 可设置 `topic` 与 `tokens`（默认≤5000），控制范围与成本。
  - 用于外部生态/库API理解；与 `codebase-retrieval`（仓内检索）严格区分。
- 输出要求：
  - 明确指出选中的库ID与选择理由；必要时给出替代项简述。

#### 10.10.3 PostgreSQL（只读查询）
- 工具：`query_PostgreSQL`（只读）。
- 使用原则：
  - 计划/执行模式下用于“架构/表结构/字段/索引/函数签名”验证；禁止用于DDL/DML与写操作。
  - 安全与成本：优先使用`LIMIT`与精确字段，避免大结果集；仅在验证必要时调用。
- 典型校验：
  - 表/字段是否存在与类型是否匹配
  - 关键函数/视图是否存在、签名是否一致

#### 10.10.4 Time（时间与时区）
- 工具：`get_current_time_Time`、`convert_time_Time`。
- 约定：
  - 默认时区：`Asia/Shanghai`（未提供时使用）。
  - 输出格式：24小时制；在日志/展示中注明时区。
- 用途：
  - 任务时间戳、审计日志、跨时区事件对齐、SLA计算。

#### 10.10.5 TaskManager（任务编排）
- 触发：多文件/跨层改动；>2次编辑-验证迭代；或用户要求展示计划/进度。
- 原则：
  - 始终保持“仅一个任务 IN_PROGRESS”；状态切换使用 `update_tasks` 批量更新（上个 COMPLETE、新的 IN_PROGRESS）。
  - 完成单项后必须等待用户 `approve_task_completion`；全部完成需 `approve_request_completion`。
- 流程：`request_planning` → `get_next_task` →（执行）→ `mark_task_done` → `approve_task_completion` → 下一个任务。

#### 10.10.6 Memory（知识图谱）
- 创建/更新：
  - 新实体：`create_entities_Memory`；更新观察：`add_observations_Memory`；关系：`create_relations_Memory`（主动语态）。
  - 删除错误记忆：`delete_entities_Memory`/`delete_relations_Memory`/`delete_observations_Memory`。
- 检索：`search_nodes_Memory`（语义/文本结合）、`open_nodes_Memory`（精确查看）。
- 规则：
  - 规则层（.memory/规则层）文档是权威来源；发现不一致以文档为准并修正记忆。
  - 每个模式结束时同步更新记忆并在任务文件中记录“记忆更新日志”。

### 10.11 按模式的端到端协作流水线 [强制]
- 研究：
  - 首读规则层文档 → Memory检索历史 → codebase-retrieval 定位仓内高层信息 → view 精读关键文件/符号 → Sequential thinking 形成问题清单与信息空白。
- 创新：
  - Sequential thinking 生成多方案并评估利弊；不产出代码；用规则层核对可行性；必要时 Context 7 获取外部库能力边界。
- 计划：
  - 用 view 验证函数签名/目录结构；用 PostgreSQL 验证表/函数签名；如涉及外部库，先 `resolve-library-id` 再 `get-library-docs`；输出详细检查清单与回滚策略；如满足触发条件则启动 TaskManager。
- 执行：
  - 严格按检查清单：view 再编辑（str-replace-editor ≤150行/批）；必要时并行只读检索；安全验证（测试/linters/type-check）可用 launch-process；更新 Memory 与文档；每步待用户确认。
- 审查：
  - 逐项对照计划；运行静态/测试工具；标记任何未报告偏差；修正记忆与文档。

### 10.12 质量与展示加固 [强制]
- 输出：所有多行代码以 `<augment_code_snippet mode="EXCERPT" path="...">` 包裹，≤10行；其余一行以内用行内反引号。
- 并行：只读查询默认并行；编辑同一文件需顺序合并，避免冲突。
- 复核：在“编辑→验证→安全运行→更新记忆/文档”闭环后再提交给用户确认。


### 10.13 工具-模式映射清单 [强制]

> 本清单规定五大模式必须优先使用/并行使用的 MCP 工具。未按清单执行需在当次响应中说明原因并获得用户同意。

- 研究（Research）
  - Sequential thinking：拆解问题与形成假设（仅内部推理）
  - Memory：检索项目记忆与规则；验证一致性
  - Context 7：外部库文档（resolve-library-id → get-library-docs）
  - PostgreSQL：只读验证表/字段/函数/视图签名
  - Time：时间戳/时区统一
  - TaskManager：当预计多轮或跨文件探索时创建“Investigate/Understand”任务

- 创新（Innovation）
  - Sequential thinking：多方案生成与利弊评估（不产出代码）
  - Memory：与规则/架构约束对齐
  - Context 7：确认外部库能力边界
  - Time：记录评审时间线

- 计划（Plan）
  - Sequential thinking：拆分实施单元、风险与回滚策略
  - TaskManager：创建任务清单，保持仅一个 IN_PROGRESS
  - Memory：对齐规则层（编码/质量/数据库规范）
  - PostgreSQL：只读校验架构/函数签名
  - Context 7：外部库用法确认
  - Time：排期与里程碑

- 执行（Execute）
  - TaskManager：逐项执行并等待用户审批
  - Sequential thinking：微小偏差的内部收敛（先报告再实施）
  - Memory：创建/更新实体与关系，文档同步
  - PostgreSQL：执行前只读核验（禁止DDL/DML）
  - Time：执行打点与耗时统计
  - Context 7：临场确认外部API/边界

- 审查（Review）
  - Sequential thinking：对照计划标注偏差与根因
  - Memory：修正/删除错误记忆，完成一致性收敛
  - PostgreSQL：只读验证结果与规范一致
  - Context 7：核对外部库调用与官方文档一致
  - Time：审计时序复盘
  - TaskManager：全部任务完成后请求关单

### 10.14 工具使用合规与记录 [强制]
本节为硬规则执行项：违反将导致审查失败。

- 并行优先：研究/创新/计划阶段的只读检索（Memory/Context 7/PostgreSQL 只读/view）默认并行；存在依赖时再串行。
- 权限边界：依赖安装、数据库/外部系统写操作、部署、产生费用的外部调用须事前获得用户明确许可。
- 编辑前验证：先用 view/搜索确认目标代码/签名/上下文，再使用 str-replace-editor 小步修改（≤150行/批）。
- 响应记录：每次响应末尾的“上下文状态”新增一行【工具使用】：
  - 记录本轮实际调用的 MCP 工具与用途（例如：Memory.search_nodes - 检索规则；PostgreSQL.query - 校验函数签名）。
  - 如未调用，标注原因（Not needed / Blocked / Waiting approval）。
- 审查要求：在审查模式核对“工具-模式映射清单”是否得到遵循，并检查【工具使用】记录是否完整。
