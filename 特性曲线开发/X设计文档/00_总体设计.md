## 1. 项目概述

### 1.1 项目目标

开发一套完整的泵特性曲线拟合系统，支持以下功能：

1. **三条核心曲线拟合**：
   - Q-H 曲线（流量-扬程）
   - Q-P 曲线（流量-功率）
   - Q-η 曲线（流量-效率）

2. **多种拟合方法**：
   - 数学方法（多项式、高斯函数等）
   - 物理机理模型（泵特性方程、功率方程等）
   - 机器学习方法（XGBoost、RandomForest等）
   - 深度学习方法（MLP、PINN等）

3. **完整的质量保障**：
   - 物理约束验证（单调性、边界条件、物理一致性）
   - 历史数据评估（时间窗口验证、分区间评估）
   - 版本管理（时间戳版本号、永久保存历史）

4. **高性能处理**：
   - 批处理（数据量>25,000点）
   - 内存缓存（LRU缓存）
   - 参数自动优化

### 1.2 功能范围

**本期实现**：
- ✅ Q-H、Q-P、Q-η 三条曲线
- ✅ 数学方法和物理机理模型
- ✅ 物理约束验证
- ✅ 版本管理和历史数据评估

**后期扩展**：
- ⏳ 机器学习方法（XGBoost、RandomForest、SVR）
- ⏳ 深度学习方法（MLP、PINN）
- ⏳ 变频泵特性曲线族（22条曲线）
- ⏳ 泵组特性曲线
- ⏳ 软启动特性曲线

### 1.3 非功能需求

| 需求类型 | 具体要求 |
|---------|---------|
| **性能** | 单次拟合耗时 < 30秒（数据量<25,000点） |
| **准确性** | R² > 0.90（多项式）、R² > 0.95（物理模型） |
| **可扩展性** | 易于添加新曲线类型和拟合方法 |
| **可维护性** | 模块独立、职责清晰、文档完整 |
| **可靠性** | 完整的错误处理和日志记录 |

## 2. 设计原则

### 2.1 核心原则

1. **模块独立性**
   - 每个曲线类型（Q-H、Q-P、Q-η）完全独立开发
   - 曲线模块间互不依赖，故障隔离
   - 便于并行开发和单独测试

2. **方法通用性**
   - 所有拟合方法通用，任何曲线都可使用任何方法
   - 通过方法注册表统一管理
   - 支持方法组合和混合

3. **依赖注入**
   - 共用组件（存储、缓存、评估等）通过主管道注入
   - 避免循环依赖
   - 便于单元测试（Mock注入）

4. **物理约束优先**
   - 90%约束参数自动计算
   - 10%支持手动覆盖
   - 允许强制拟合（带警告）

5. **智能默认 + 高级可控**
   - 自动决策预处理步骤（归一化、特征工程）
   - 支持手动覆盖所有自动决策
   - 降低使用门槛，满足高级需求

### 2.2 编码规范

遵循项目现有编码规范：

- ✅ 所有注释和日志使用中文
- ✅ 单文件不超过600行
- ✅ 禁止使用代码占位符（如`pass`、`TODO`）
- ✅ 遵循单一职责原则
- ✅ 使用类型注解（Type Hints）
- ✅ 完整的错误处理和日志记录

## 4. 技术选型

### 4.1 核心技术栈

| 技术领域 | 选型 | 理由 |
|---------|------|------|
| **编程语言** | Python 3.9+ | 项目现有技术栈 |
| **数据处理** | pandas, numpy | 高效的数据处理和数值计算 |
| **数学拟合** | scipy.optimize | 成熟的优化和拟合库 |
| **数据库** | PostgreSQL | 项目现有数据库 |
| **缓存** | functools.lru_cache | 内存LRU缓存，无需Redis |
| **日志** | logging | Python标准库 |
| **类型注解** | typing | 提高代码可读性和IDE支持 |

### 4.2 拟合方法技术选型

| 方法类别 | 具体方法 | 技术实现 | 适用场景 |
|---------|---------|---------|---------|
| **数学方法** | 多项式回归 | numpy.polyfit | 通用拟合，快速 |
| **数学方法** | 高斯函数 | scipy.optimize.curve_fit | Q-η曲线（单峰） |
| **物理机理** | 泵特性方程 | scipy.optimize.curve_fit | Q-H曲线（物理模型） |
| **物理机理** | 功率方程 | 能量守恒公式 | Q-P曲线（依赖Q-H和Q-η） |
| **机器学习** | XGBoost | xgboost库 | 复杂非线性关系（后期） |
| **深度学习** | PINN | PyTorch/TensorFlow | 物理约束神经网络（后期） |

### 4.3 数据库设计选型

- **表结构**：三表分离设计（`curve_fit_results` 主表 + `curve_fit_params` 参数表 + `curve_fit_metrics` 指标表）
- **版本号**：时间戳格式（YYYYMMDD_HHMMSS），精确到秒
- **JSONB字段**：保留用于复杂结构（physics_validation、historical_evaluation、normalization_params）
- **索引策略**：device_id + curve_type + version 复合唯一索引，外键索引
- **视图**：`curve_fit_latest`（最新版本）、`v_curve_fit_full`（完整拟合结果）

## 6. 数据流程

### 6.1 拟合流程图

```
用户调用
    ↓
[1] 主管道接收请求
    ↓
[2] 选择曲线模块（QH/QP/QEta）
    ↓
[3] 数据提取（DataExtractor）
    │   - 从fact_measurements提取数据
    │   - 应用缓存（CacheManager）
    │   - 批处理（BatchProcessor，如果>25,000点）
    ↓
[4] 数据预处理（Preprocessor）
    │   - 数据清洗（删除无效值、重复值）
    │   - 归一化（根据方法需求自动决策）
    │   - 特征工程（根据方法需求自动决策）
    ↓
[5] 物理约束计算（Constraints）
    │   - 自动计算约束参数（H₀、Q_max等）
    │   - 支持手动覆盖
    ↓
[6] 曲线拟合（CurveFitter）
    │   - 遍历所有指定方法
    │   - 应用物理约束
    │   - 参数优化（如果启用）
    │   - 选择最佳结果（R²最高）
    ↓
[7] 结果验证（Validator）
    │   - 单调性验证
    │   - 边界条件验证
    │   - 物理一致性验证
    ↓
[8] 结果存储（ResultStorage）
    │   - 生成版本号（时间戳）
    │   - 保存到数据库
    ↓
[9] 历史数据评估（HistoricalDataEvaluator）
    │   - 使用测试数据评估
    │   - 计算偏差统计
    │   - 分区间评估
    ↓
[10] 结果输出（ResultOutput）
    │   - 格式化输出
    │   - 生成报告
    │   - 可视化（可选）
    ↓
返回结果
```

### 6.2 数据流详细说明

| 步骤 | 输入 | 输出 | 关键操作 |
|-----|------|------|---------|
| **1. 主管道** | device_id, curve_type, start_time, end_time, methods | 曲线实例 | 依赖注入共用组件 |
| **2. 选择曲线** | curve_type | QHCurve/QPCurve/QEtaCurve | 工厂模式 |

| **7. 验证** | FitResult, 约束 | ValidationResult | 单调性、边界、物理一致性 |
| **8. 存储** | FitResult | version | 插入数据库 |
| **9. 评估** | FitResult, 测试数据 | EvaluationReport | 偏差统计、分区间评估 |
| **10. 输出** | FitResult, EvaluationReport | 格式化结果 | JSON/报告/图表 |

## 8. 关键设计决策

### 8.1 为什么选择模块独立性？

**问题**：三条曲线（Q-H、Q-P、Q-η）是否应该共享代码？

**决策**：完全独立，每个曲线一个独立模块

**理由**：
1. ✅ **开发简单**：每个曲线独立开发，互不影响
2. ✅ **故障隔离**：一个曲线出问题不影响其他曲线
3. ✅ **并行开发**：多人可同时开发不同曲线
4. ✅ **灵活扩展**：添加新曲线只需新增模块
5. ⚠️ **代码重复**：可接受的代价（通过共用层减少重复）

### 8.2 为什么选择方法通用性？

**问题**：拟合方法是否应该绑定到特定曲线？

**决策**：所有方法通用，通过注册表管理

**理由**：
1. ✅ **灵活性**：任何曲线都可尝试任何方法
2. ✅ **可扩展性**：添加新方法只需注册
3. ✅ **实验友好**：方便对比不同方法的效果
4. ✅ **代码复用**：方法实现只写一次

### 8.3 为什么选择时间戳作为版本号？

**问题**：版本号应该用递增整数还是时间戳？

**决策**：时间戳（YYYYMMDD_HHMMSS）

**理由**：
1. ✅ **可读性**：一眼看出拟合时间
2. ✅ **唯一性**：精确到秒，几乎不会冲突
3. ✅ **排序性**：字符串排序即时间排序
4. ✅ **无需维护**：不需要查询最大版本号

### 8.4 为什么选择JSONB存储拟合参数？

**问题**：拟合参数应该用单独的表还是JSONB字段？

**决策**：JSONB字段

**理由**：
1. ✅ **灵活性**：不同方法参数结构不同
2. ✅ **简单性**：避免复杂的表关联
3. ✅ **查询性能**：PostgreSQL的JSONB支持索引
4. ✅ **扩展性**：添加新方法不需要修改表结构

### 8.5 为什么选择历史数据评估而非R²？

**问题**：如何评估拟合质量？

**决策**：历史数据评估为主，R²为辅

**理由**：
1. ✅ **实用性**：直接反映预测偏差
2. ✅ **可解释性**：偏差百分比更直观
3. ✅ **分区间评估**：发现局部问题
4. ⚠️ **R²仍保留**：作为参考指标

### 8.6 为什么选择内存缓存而非Redis？

**问题**：缓存应该用Redis还是内存？

**决策**：内存LRU缓存（functools.lru_cache）

**理由**：
1. ✅ **简单性**：无需额外部署Redis
2. ✅ **性能**：内存访问更快
3. ✅ **适用性**：数据量不大，内存足够
4. ⚠️ **局限性**：进程重启缓存丢失（可接受）

## 9. 风险和注意事项

### 9.1 技术风险

| 风险 | 影响 | 缓解措施 |
|-----|------|---------|
| **数据质量差** | 拟合失败或精度低 | 充分的数据清洗和验证 |
| **计算性能** | 大数据量拟合慢 | 批处理、缓存、参数优化 |
| **物理约束冲突** | 拟合结果不符合物理规律 | 允许强制拟合（带警告） |
| **版本管理复杂** | 历史版本过多 | 定期归档、状态管理 |

### 9.2 开发风险

| 风险 | 影响 | 缓解措施 |
|-----|------|---------|
| **模块依赖混乱** | 难以维护 | 严格遵循依赖注入原则 |
| **代码重复** | 维护成本高 | 通过共用层减少重复 |
| **测试不充分** | 质量问题 | 完整的单元测试和集成测试 |
| **文档不同步** | 理解困难 | 代码即文档、及时更新 |
