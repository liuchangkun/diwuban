## 📋 任务概述

### 核心目标
基于时间序列数据自动计算设备的运行状态阈值,并准确识别四种状态:
1. **运行稳态** (running steady-state, phase=1)
2. **停止稳态** (stopped steady-state, phase=0)
3. **启动中** (starting transition, phase=2)
4. **停止中** (stopping transition, phase=3)

### 技术约束
1. **多信号融合**: 阈值计算必须综合考虑频率(pump_frequency)、电流(pump_current_a/b/c)、功率(pump_active_power)三个信号的关系
2. **复杂场景处理**: 需要处理多台泵同时运行的场景,此时功率、电流、频率之间不是简单的线性比例关系
3. **设备类型识别**: 必须自动区分两种设备类型:
   - 变频泵(VFD pump): 频率可变(通常45-50Hz),需要使用频率+电流+功率三信号融合
   - 软启动泵(soft-start pump): 频率恒定(50Hz),只能使用电流+功率双信号融合
4. **时间对齐问题**: 当前数据采集从设备启动时刻开始,缺少启动前的低电流/低功率/低频率数据

### 问题案例
- **设备**: device_id=5
- **时间段**: 2025-06-01 02:00:00-04:00:00
- **现象**: 频率46-49Hz(100%时间),功率214-291kW(100%时间),电流平均397A,但运行状态判定只识别出2.2%的运行时间(156/7200秒)
- **根本原因**: Otsu双峰法假设有"运行/停止"两个峰值,但device_id=5持续运行(单峰分布),导致阈值i_on=441.92A过高(实际运行电流平均397A)

## 🔍 研究模式 - 现状分析

### 1. 数据库表结构分析

#### 1.1 device_running_thresholds 表
**用途**: 存储设备运行状态判定的阈值配置

**核心字段**:
```sql
device_id            bigint PRIMARY KEY
enable_i/p/f         boolean  -- 是否启用电流/功率/频率判断
i_on/i_off           double precision  -- 电流开启/关闭阈值
p_on/p_off           double precision  -- 功率开启/关闭阈值
f_on/f_off           double precision  -- 频率开启/关闭阈值
grace_hold_secs      integer  -- 数据缺失容忍时间(默认30秒)
min_run_secs         integer  -- 最小运行时间(默认10秒)
min_stop_secs        integer  -- 最小停止时间(默认10秒)
smoothing_secs       integer  -- 平滑窗口(默认5秒)
start_pre_secs       integer  -- 启动前窗口(用于识别phase=2)
start_post_secs      integer  -- 启动后窗口(用于识别phase=2)
stop_pre_secs        integer  -- 停止前窗口(用于识别phase=3)
stop_post_secs       integer  -- 停止后窗口(用于识别phase=3)
```

**设计特点**:
- 支持三信号独立开关(enable_i/p/f)
- 使用滞回带(on/off双阈值)避免抖动
- 包含时间参数用于过渡状态识别

**当前问题**:
- 缺少设备类型字段(无法区分变频泵 vs 软启动泵)
- 缺少信号融合策略字段(无法配置多信号组合逻辑)
- start_pre_secs/start_post_secs等字段存在但未被充分利用

#### 1.2 mv_device_running_1s 表
**用途**: 存储设备逐秒运行状态和相位信息

**核心字段**:
```sql
station_id, device_id, ts_bucket  -- 主键
running              smallint  -- 运行状态(0/1)
phase                smallint  -- 相位(0=停止稳态, 1=运行稳态, 2=启动中, 3=停止中)
phase_type           text      -- 相位类型(预留字段)
```

**生成逻辑**:
- 由 `sp_refresh_mv_running_phase` 存储过程生成
- 基于 `fn_running_state_1s` 函数的运行判定结果
- 通过检测运行状态边沿(0→1, 1→0)识别启动/停止时刻
- 在边沿前后扩展窗口标记过渡状态(phase=2/3)

**当前问题**:
- phase=2(启动中)的识别依赖启动前数据,但数据采集从启动时刻开始,导致无法准确识别
- phase_type字段未使用,缺少对过渡状态的细分(如"正常启动"vs"异常启动")

### 2. 阈值学习算法分析

#### 2.1 电流阈值学习 (sp_refresh_device_running_thresholds_current)

**算法流程**:
```
1. 读取三相电流数据(pump_current_a/b/c),取最大值
2. 使用Otsu双峰法(简化版:中位数)计算分割阈值
3. 计算滞回带: 2 * MAD(中位数绝对偏差)
4. i_on = 阈值 + 滞回带
5. i_off = 阈值 - 滞回带
```

**回退机制**:
1. 优先从设备自己的历史数据学习(需要 >= 50个样本)
2. 如果样本不足,使用同类型设备的中位数
3. 如果同类型设备也没有,使用全局中位数
4. 如果全局也没有,保持NULL(不启用电流判断)

**数据筛选**:
- 只使用 quality_status=0 的数据
- 只使用稳态数据(phase=1 或 running=1)
- 最小样本数: 50

**核心问题**:
1. **Otsu双峰法的局限性**:
   - 假设数据分布有两个明显的峰值(运行峰 + 停止峰)
   - 对于持续运行的设备(单峰分布),会错误地将中位数作为阈值
   - 对于频繁启停的设备(双峰分布),效果较好
   - 对于偶尔运行的设备(混合分布),可能产生偏差

2. **缺少设备类型识别**:
   - 未区分变频泵 vs 软启动泵
   - 未根据设备类型调整阈值学习策略

3. **单信号独立学习**:
   - 电流、功率、频率阈值分别独立学习
   - 未考虑三信号之间的相关性
   - 未处理多台泵同时运行时的信号叠加问题

#### 2.2 功率阈值学习 (sp_refresh_device_running_thresholds_power)

**算法**: 与电流阈值学习类似,但默认设置 `enable_p = FALSE`

**设计理由**: 电流判断已足够,功率判断作为备用

**问题**: 
- 对于多台泵并联运行的场景,总管功率分摊导致单泵功率不准确
- 未考虑功率与电流、频率的关系(P ∝ I × V, P ∝ Q × H ∝ f³)

#### 2.3 频率阈值学习 (sp_refresh_device_running_thresholds_frequency)

**算法**: 与电流阈值学习类似,但默认设置 `enable_f = FALSE`

**问题**:
- 对于软启动泵,频率恒定50Hz,无法用于运行判断
- 对于变频泵,频率是重要的运行指标,但当前未充分利用
- 未自动识别设备类型并调整enable_f设置

### 3. 运行状态判定逻辑分析

#### 3.1 fn_running_state_1s 函数

**核心逻辑**:
```sql
-- 运行判定(OR逻辑)
v_state := ( (v_ei AND r_max_i >= v_i_on)
          OR (v_ep AND r_p     >= v_p_on)
          OR (v_ef AND r_f     >= v_f_on) );

-- 滞回判定
IF v_state THEN  -- 当前运行
  IF (所有启用信号 <= off阈值) THEN v_state := false; END IF;
ELSE  -- 当前停止
  IF (任一启用信号 >= on阈值) THEN v_state := true; END IF;
END IF;
```

**特点**:
- 使用OR逻辑组合多信号(任一信号满足即判定为运行)
- 支持滞回避免抖动
- 支持数据缺失容忍(grace_hold_secs)

**问题**:
1. **OR逻辑的局限性**:
   - 无法处理信号冲突(如电流高但功率低)
   - 无法利用信号之间的相关性
   - 容易产生误判(如单个信号异常导致错误判定)

2. **缺少信号权重**:
   - 所有信号平等对待
   - 未根据信号可靠性调整权重

3. **缺少设备类型适配**:
   - 变频泵和软启动泵使用相同的判定逻辑
   - 未根据设备类型选择合适的信号组合

### 4. 过渡状态识别逻辑分析

#### 4.1 sp_refresh_mv_running_phase 存储过程

**识别逻辑**:
```sql
-- 检测运行状态边沿
edges: 0→1 (启动边沿), 1→0 (停止边沿)

-- 标记过渡状态
phase = CASE
  WHEN is_running THEN 1  -- 运行稳态
  WHEN 在启动边沿前 v_startup_secs 秒内 THEN 2  -- 启动中
  WHEN 在停止边沿后 v_shutdown_secs 秒内 THEN 3  -- 停止中
  ELSE 0  -- 停止稳态
END
```

**默认参数**:
- v_startup_secs = 10秒
- v_shutdown_secs = 10秒

**核心问题**:
1. **启动中(phase=2)识别失败**:
   - 需要"启动边沿前"的数据
   - 但数据采集从启动时刻开始,缺少启动前的低电流/低功率数据
   - 导致phase=2几乎无法被识别

2. **固定时间窗口**:
   - 使用固定的10秒窗口
   - 未根据设备特性(如大型泵 vs 小型泵)调整窗口大小
   - 未根据实际启动/停止过程的持续时间动态调整

3. **缺少过渡状态验证**:
   - 未验证过渡状态期间的信号变化特征
   - 未区分"正常启动"vs"异常启动"

### 5. filter_running参数的影响分析

**使用场景**: 在缺失指标计算中,`filter_running=True`时只使用运行中的设备数据

**影响**:
- pump_flow_rate等指标的计算依赖准确的运行状态判定
- 如果运行状态判定错误(如只识别出2.2%的运行时间),会导致:
  - 可用数据大幅减少
  - 计算结果不准确
  - 指标计算失败率上升

**示例** (来自代码):
```python
# orchestrator.py line 1687-1704
if filter_running:
    cur.execute("""
        SELECT fm.ts_bucket, fm.device_id, ...
        FROM fact_measurements fm
        JOIN mv_device_running_1s dr
          ON dr.station_id = fm.station_id
         AND dr.device_id = fm.device_id
         AND dr.ts_bucket = fm.ts_bucket
        WHERE dr.running = 1  -- 只使用运行中的数据
    """)
```

## 📊 关键发现总结

### 发现1: Otsu双峰法不适用于持续运行场景
- **问题**: device_id=5持续运行,数据呈单峰分布,Otsu法错误地将中位数作为阈值
- **影响**: i_on=441.92A过高,实际运行电流397A被判定为停止
- **根本原因**: 算法假设有"运行峰+停止峰",但实际只有"运行峰"

### 发现2: 缺少设备类型自动识别
- **问题**: 未区分变频泵 vs 软启动泵
- **影响**: 
  - 软启动泵的频率恒定50Hz,但enable_f仍可能被启用
  - 变频泵的频率是重要指标,但enable_f默认为FALSE
- **需求**: 自动识别设备类型并调整信号使用策略

### 发现3: 单信号独立学习忽略信号相关性
- **问题**: 电流、功率、频率阈值分别独立学习
- **影响**: 
  - 未利用P ∝ I × V的关系
  - 未利用P ∝ f³的关系(变频泵)
  - 多台泵并联时信号叠加问题未处理

### 发现4: OR逻辑组合信号存在局限
- **问题**: 任一信号满足即判定为运行
- **影响**: 
  - 单个信号异常导致误判
  - 无法处理信号冲突
  - 无法利用信号一致性提高判定可靠性

### 发现5: 启动中状态识别失败
- **问题**: 数据采集从启动时刻开始,缺少启动前数据
- **影响**: phase=2几乎无法被识别
- **需求**: 提出替代方案识别启动过渡状态
