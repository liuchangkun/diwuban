## 🔴 严重问题（P0 - 必须立即修复）

### 问题1: 运行状态过滤未实现
- **位置**: `app/services/calculation/orchestrator.py` 第66-178行 `load_data` 方法
- **问题描述**: 
  - 查询fact_measurements时未过滤设备运行状态
  - 可能包含设备停机时的数据
  - 停机数据会严重影响计算结果准确性
- **影响**: 
  - 计算结果不准确
  - 可能导致错误的流量、功率等指标
- **违反规则**: 业务逻辑要求只计算运行状态数据
- **修复建议**:
  ```sql
  -- 添加运行状态过滤
  JOIN mv_device_running_1s dr 
    ON fm.station_id = dr.station_id 
    AND fm.device_id = dr.device_id 
    AND fm.ts_bucket = dr.ts_bucket
  WHERE dr.is_running = TRUE
  ```
- **优先级**: P0
- **预估工时**: 2小时

### 问题2: quality_status过滤未实现
- **位置**: `app/services/calculation/orchestrator.py` 第66-178行 `load_data` 方法
- **问题描述**:
  - 查询fact_measurements时未过滤quality_status
  - 可能包含质量问题数据（quality_status != 0）
  - 质量问题数据会导致计算结果不可靠
- **影响**:
  - 计算结果不可靠
  - 可能传播质量问题到计算指标
- **违反规则**: 质量控制要求只使用quality_status=0的数据
- **修复建议**:
  ```sql
  WHERE quality_status = 0
  ```
- **优先级**: P0
- **预估工时**: 1小时

### 问题3: 直接SQL查询违反项目规则
- **位置**: `app/services/calculation/orchestrator.py` 多处
- **问题描述**:
  - 直接在Python代码中编写SQL查询
  - 违反项目规则：所有数据操作必须通过存储过程
- **影响**:
  - 违反架构约束
  - 难以维护和优化
  - 无法利用数据库层面的优化
- **违反规则**: `.memory/规则层/项目规则.md` 第90-95行
  ```
  ### [强制] 数据操作规范
  - 所有数据表的CRUD操作必须通过 `api` schema 的存储过程
  - **禁止**在应用代码中直接写SQL的INSERT/UPDATE/DELETE
  - 查询操作优先使用 `reporting` schema 的物化视图或函数
  ```
- **修复建议**:
  - 创建 `reporting.fn_get_calculation_data` 存储过程
  - 创建 `api.sp_write_calculated_metrics` 存储过程
  - 重构orchestrator.py使用存储过程
- **优先级**: P0
- **预估工时**: 8小时

### 问题4: 缺少API端点
- **位置**: `app/api/v1/` 目录
- **问题描述**:
  - 缺失指标计算功能没有对应的API端点
  - 只能通过CLI使用，无法集成到Web应用
  - 无法通过HTTP接口触发计算
- **影响**:
  - 功能无法集成到前端应用
  - 无法实现自动化调度
  - 用户体验差
- **修复建议**:
  - 创建 `app/api/v1/calculation.py`
  - 实现以下端点:
    - POST /api/v1/calculation/missing-metrics - 触发计算
    - GET /api/v1/calculation/status/{run_id} - 查询计算状态
    - GET /api/v1/calculation/methods - 获取可用方法
    - GET /api/v1/calculation/parameters - 获取参数配置
- **优先级**: P0
- **预估工时**: 6小时
