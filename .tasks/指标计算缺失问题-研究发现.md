### 2. 根本原因分析

#### 🔴 **核心问题：mv_device_running_1s 表数据不一致**

**发现**:
1. 数据库中只有一个泵站：`station_id=14`（二期供水泵房）
2. `fact_measurements` 表中有 511,200 行 `station_id=14` 的数据
3. **但是 `mv_device_running_1s` 表中 `station_id=14` 的数据为 0 行**
4. `mv_device_running_1s` 表中只有 `station_id=12` 的数据（43,194 行）
5. `fact_measurements` 表中 `station_id=12` 的数据为 0 行

**这是一个严重的数据不一致问题：运行状态表和事实表的 station_id 不匹配！**

#### 🔴 **计算流程依赖 mv_device_running_1s 表**

查看 `app/services/calculation/orchestrator.py` 代码发现：

1. **load_data 方法默认 `filter_running=True`**:
```python
def load_data(
    self,
    station_id: int,
    device_id: int,
    start_time: str,
    end_time: str,
    metric_keys: List[str],
    filter_running: bool = True,  # 默认过滤停机数据
    filter_quality: bool = True,
) -> tuple[Dict[str, np.ndarray], np.ndarray]:
```

2. **当 `filter_running=True` 时，SQL 查询使用 INNER JOIN**:
```sql
SELECT fm.ts_bucket, fm.metric_id, fm.value
FROM fact_measurements fm
INNER JOIN mv_device_running_1s dr
    ON fm.station_id = dr.station_id
    AND fm.device_id = dr.device_id
    AND fm.ts_bucket = dr.ts_bucket
WHERE fm.station_id = %s
  AND fm.device_id = %s
  AND fm.ts_bucket >= %s::timestamptz
  AND fm.ts_bucket < %s::timestamptz
  AND fm.metric_id = ANY(%s)
  AND dr.running = 1
```

3. **结果**:
   - 由于 `mv_device_running_1s` 表中没有 `station_id=14` 的数据
   - INNER JOIN 导致查询结果为空
   - 无法加载任何依赖数据
   - 无法计算任何需要依赖数据的指标

#### 🔴 **为什么 pump_outlet_pressure 能计算成功？**

查看计算方法注册表：
```sql
method_id='pump_outlet_pressure_method_b'
dependencies=['main_pipeline_outlet_pressure']
```

**原因**:
- `pump_outlet_pressure_method_b` 的依赖是 `main_pipeline_outlet_pressure`
- 这个依赖可能是泵站级数据，不需要设备级的运行状态过滤
- 或者该方法的实现绕过了 `filter_running` 检查

### 3. 数据流程梳理

#### 3.1 run-all 命令执行流程

根据 `configs/merge.yaml` 和代码分析：

```
1. prepare-dim (stage 1)
   ↓
2. create-staging
   ↓
3. ingest-copy (导入 CSV 数据)
   ↓

   ↓

   ↓

```

## 🎯 结论

### 根本原因

**device_running_thresholds 表为空，导致 mv_device_running_1s 表无数据**:

1. **当前数据库状态**:
   - dim_devices 表中有设备 105-110（station_id=14）
   - fact_measurements 表中有 511,200 行 station_id=14 的数据
   - **device_running_thresholds 表完全为空（0 行）**
   - **mv_device_running_1s 表中只有 station_id=12 的旧数据（43,194 行）**
   - mv_device_running_1s 表中没有 station_id=14 的数据

2. **历史背景**（根据修复报告）:
   - 之前数据库中有设备 89-94（station_id=12）
   - 2025-10-23 修复了 mv_device_running_1s 表的 ID 映射错误
   - 修复后为设备 89-94 创建了阈值配置
   - 重新生成了 station_id=12 的运行状态数据

3. **当前问题**:
   - 数据库已经更新，现在使用设备 105-110（station_id=14）
   - **但是 device_running_thresholds 表没有为新设备创建配置**
   - 导致 device_running 步骤无法为新设备生成运行状态数据
   - mv_device_running_1s 表中仍然只有旧设备（89-94）的数据

4. **计算流程失败的原因**:
   - 计算流程默认使用 `filter_running=True`
   - SQL 查询使用 INNER JOIN mv_device_running_1s
   - 由于 mv_device_running_1s 中没有 station_id=14 的数据
   - INNER JOIN 返回空结果
   - 无法加载任何依赖数据
   - 所有需要依赖数据的指标计算失败

### 影响范围

1. **直接影响**: 所有需要依赖数据的指标计算失败（pump_flow_rate, pump_head, pump_efficiency, pump_speed, pump_torque, pump_cumulative_flow）
2. **间接影响**: 依赖这些计算指标的下游指标也无法计算
3. **数据完整性**: mv_device_running_1s 表包含过时的设备数据（89-94），缺少当前设备数据（105-110）

### 已验证的事实

1. ✅ dim_devices 表中只有设备 105-110（station_id=14）
2. ✅ fact_measurements 表中只有 station_id=14 的数据
3. ✅ device_running_thresholds 表完全为空
4. ✅ mv_device_running_1s 表中只有 station_id=12 的旧数据
5. ✅ 计算流程的代码逻辑是正确的
6. ✅ 存储过程的逻辑是正确的
