### 问题1：外键约束处理策略矛盾 ⚠️ **严重**

**问题描述**：
- 用户说"可以删除 TRUNCATE CASCADE，因为 prepare-dim 会自动更新所有关联表"
- 但如果不使用 TRUNCATE CASCADE，删除维度表数据时会因为外键约束而失败
- 当前有29个外键约束引用维度表

**影响范围**：
- dim_stations 被引用6次
- dim_devices 被引用9次
- dim_metric_config 被引用8次

**解决方案**：
1. **方案A**：使用 `DELETE CASCADE`（在外键定义中添加 ON DELETE CASCADE）
2. **方案B**：按照依赖顺序手动删除（先删除依赖表，再删除维度表）
3. **方案C**：临时禁用外键约束（`SET CONSTRAINTS ALL DEFERRED`）

**推荐**：方案B（手动管理依赖顺序），因为：
- 更安全，不会静默删除数据
- 符合用户需求6"给出提示，通过CLI命令进行更新"
- 可以在删除前备份重要数据

### 问题2：规则生成的执行时机冲突 ⚠️ **严重**

**问题描述**：
- 用户要求将规则生成逻辑合并到 prepare-dim 中
- 但规则生成依赖 fact_measurements 中的历史数据
- prepare-dim 在 merge-fact 之前执行（根据 merge.yaml 配置）
- 如果在 prepare-dim 中生成规则，此时 fact_measurements 可能没有数据或数据不足

**当前流程**（merge.yaml）：
```
1. prepare_dim: true  → 重建维度表
2. ingest_copy: true  → 导入CSV到staging
3. merge_fact: true   → 合并到fact_measurements
4. enable_calculation: true → 计算缺失指标
```

**矛盾点**：
- 规则生成需要在 merge-fact 之后执行（需要历史数据）
- 但 prepare-dim 在 merge-fact 之前执行

**解决方案**：
1. **方案A**：prepare-dim 分两阶段执行
   - 阶段1：重建维度表（在 merge-fact 前）
   - 阶段2：生成规则和参数（在 merge-fact 后）
2. **方案B**：prepare-dim 只在系统初始化时执行一次
   - 不在每次 merge-fact 前执行
   - 作为独立的初始化命令
3. **方案C**：规则生成使用现有历史数据
   - 假设 fact_measurements 中已有足够的历史数据
   - 如果没有数据，跳过规则生成

**推荐**：方案A（分两阶段执行），因为：
- 符合用户需求"prepare-dim 需要自动执行规则生成和参数初始化"
- 保证规则生成有足够的数据
- 逻辑清晰，易于维护

### 问题3：completion_runs 和 completion_steps 表的数据来源缺失 ⚠️ **中等**

**问题描述**：
- 用户需求1要求重建这两个表的数据
- 但这两个表是由应用代码自动生成的（device_running_job.py）
- 没有独立的CLI命令或SQL脚本可以重建历史数据

**表用途**：
- completion_runs：记录数据补全任务的执行情况
- completion_steps：记录任务的详细步骤

**数据生成方式**：
- 由 `app/services/device_running_job.py` 在运行时自动插入
- 每次执行设备运行状态计算时创建新记录

**解决方案**：
1. **方案A**：不重建这两个表的数据
   - 这两个表是审计表，记录历史执行情况
   - 维度表重建后，旧的审计记录仍然有效（通过 device_id 关联）
   - 如果 device_id 变化，旧记录会失效，但这是预期行为
2. **方案B**：在 prepare-dim 中清空这两个表
   - 维度表重建后，旧的审计记录无效
   - 清空后重新开始记录
3. **方案C**：保留这两个表的数据，不做任何处理
   - 可能存在引用已删除设备的脏数据
   - 但不影响系统功能

**推荐**：方案C（保留数据），因为：
- 审计表的历史记录有价值
- 即使 device_id 变化，仍可通过 device_name 追溯
- 不影响系统功能

### 问题6：calculation_parameters 表的数据保护 ⚠️ **严重**

**问题描述**：
- 用户需求1要求重建 calculation_parameters 表
- 但这个表存储优化后的参数（通过 parameter_optimizer.py 优化生成）
- 如果清空重建，会丢失所有优化后的参数

   - 使用 RLS 算法优化

**解决方案**：

2. **方案B**：清空所有参数，重新初始化
   - 丢失所有优化后的参数

3. **方案C**：备份优化后的参数，重建后恢复
   - 需要处理 device_id 变化的情况

**推荐**：方案A（保留设备级参数），因为：

### 问题10：事务边界设计 ⚠️ **中等**

**问题描述**：
- prepare-dim 如果包含以下操作，会形成一个非常长的事务：
  1. 清空维度表
  2. 重建维度表
  3. 清空依赖表
  4. 重建依赖表
  5. 生成规则
  6. 初始化参数

**风险**：
- 事务时间长，可能导致锁等待
- 中间任何一步失败，需要全部回滚
- 数据库连接可能超时

**解决方案**：
1. **方案A**：全部在一个事务中
   - 优点：数据一致性强
   - 缺点：事务时间长，风险高
2. **方案B**：分多个事务
   - 每个步骤一个事务
   - 优点：事务时间短
   - 缺点：中间失败时数据不一致
3. **方案C**：使用保存点（SAVEPOINT）
   - 可以部分回滚
   - 优点：灵活
   - 缺点：实现复杂

**推荐**：方案B（分多个事务），因为：
- 每个步骤相对独立
- 失败时可以从失败的步骤重新开始
- 降低锁等待风险
