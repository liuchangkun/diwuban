## 🔍 方法选择流程

### 核心逻辑（method_selector.py:252-390）

```python
def select_method(
    metric_key: str,
    available_metrics: List[str],
    context: Dict[str, Any],
    data: Optional[Dict[str, np.ndarray]] = None
) -> Optional[Dict[str, Any]]:
    """
    按优先级从高到低遍历所有方法，选择第一个满足依赖和条件的方法。
    """
    methods = self._method_registry[metric_key]  # 按priority DESC排序
    
    for method in methods:
        # 步骤1：检查设备类型适配性
        if device_type and allowed_types and device_type not in allowed_types:
            continue
        
        # 步骤2：检查依赖（包括数据有效性检查）
        if not self.check_dependencies(method['dependencies'], available_metrics, data):
            continue
        
        # 步骤3：检查条件
        if not self.check_conditions(method['conditions'], context):
            continue
        
        # 找到合适的方法
        return method
    
    # 没有找到合适的方法
    return None
```

## 📌 关键发现

### 发现1：依赖检查包含数据有效性检查

**代码位置**：`method_selector.py:159-166`

```python
# 对于特定指标，检查是否有非零值（频率、功率等）
if any(keyword in dep.lower() for keyword in ['frequency', 'power', 'flow']):
    valid_data = dep_data[valid_mask]
    non_zero_count = np.sum(valid_data > 0)
    if non_zero_count == 0:
        logger.debug(f"依赖指标 {dep} 的所有有效数据都是0或负数")
        return False
```

**影响**：
- 即使依赖指标存在，如果值为0，也会被判定为"依赖不满足"
- 这是**第三层过滤**（前两层：阈值过滤、硬编码阈值）

### 发现2：running_count来自mv_device_running_1s表

**代码位置**：`orchestrator.py:1397-1399`

```python
running_count = self._get_running_device_count(
    station_id=station_id, start_time=start_time, end_time=end_time

```

**查询结果**：
- 2025-10-23 10:48:08时刻，running_count = 6
- 这是基于mv_device_running_1s表的running=1的设备数量
- **用户手动修改running=1生效了**，所以running_count=6

### 发现3：方法C的条件检查失败

**方法C**：单泵运行直接取总管流量
- 条件：`running_count.exact: 1`
- 实际：running_count = 6
- 结果：条件不满足 ❌

**如果只有1台泵运行**：
- 方法C会被选中
- 直接取main_pipeline_flow_rate作为pump_flow_rate
- 不需要功率和频率数据

## 🔥 深度分析：三层过滤机制

### 第一层：数据加载过滤（orchestrator.py:228-242）

**过滤条件**：`mv_device_running_1s.running = 1`

**设备1的情况**：
- 用户手动修改：running = 1 ✅
- 结果：数据成功加载

**影响**：
- 控制哪些设备的数据被加载到内存
- 用户可以通过修改mv_device_running_1s表控制

---

### 第二层：计算阶段阈值过滤（orchestrator.py:1676-1681）

**过滤条件**：`freq >= 3.0 Hz AND power >= 0.5 kW`

**设备1的情况**：
- freq = 0 Hz < 3.0 Hz ❌
- power = 0 kW < 0.5 kW ❌
- 结果：权重为0，无法计算pump_flow_rate

**影响**：
- 只在pump_flow_rate_method_a中生效
- 用户无法通过修改表控制（硬编码）

---

### 第三层：方法选择依赖检查（method_selector.py:159-166）

**过滤条件**：`frequency/power/flow类指标的值 > 0`

**设备1的情况**：
- pump_active_power = 0 → non_zero_count = 0 ❌
- pump_frequency = 0 → non_zero_count = 0 ❌
- 结果：所有需要这些依赖的方法都被跳过

**影响**：
- 影响所有计算方法的选择
- 即使数据加载成功，方法选择也会失败

---

## 🎯 三层过滤的关系

```
数据加载过滤（第一层）
    ↓
    ✅ 设备1的数据被加载（running=1）
    ↓
方法选择依赖检查（第三层）
    ↓
    ❌ 方法A/D/E被跳过（power=0, freq=0）
    ❌ 方法B被跳过（pump_cumulative_flow不存在）
    ❌ 方法C被跳过（running_count=6, 需要exact:1）
    ↓
    返回None → 计算失败
    ↓
计算阶段阈值过滤（第二层）
    ↓
    ⚠️ 未执行（因为方法选择已失败）
```

**关键观察**：
- 第三层过滤比第二层更早执行
- 第三层过滤更严格（要求 > 0，而不是 >= 3.0）
- 即使绕过第二层，第三层也会阻止计算

## 🔍 依赖数据有效性检查的合理性分析

### 检查逻辑（method_selector.py:159-166）

```python
# 对于特定指标，检查是否有非零值（频率、功率等）
if any(keyword in dep.lower() for keyword in ['frequency', 'power', 'flow']):
    valid_data = dep_data[valid_mask]
    non_zero_count = np.sum(valid_data > 0)
    if non_zero_count == 0:
        logger.debug(f"依赖指标 {dep} 的所有有效数据都是0或负数")
        return False
```

### 设计意图

**合理性**：
- ✅ 避免使用无效数据进行计算（如功率=0时无法进行功率分摊）
- ✅ 提前过滤掉不可行的方法，避免后续计算错误
- ✅ 符合物理意义（停机设备的功率和频率应该是0）

**问题**：
- ❌ 对于停机设备，这个检查会导致所有方法都被跳过
- ❌ 没有区分"数据缺失"和"数据为0"的情况
- ❌ 停机设备的流量应该是0，而不是"无法计算"

### 建议

**方案1**：为停机设备添加特殊处理
- 检测到所有依赖数据都是0时，直接返回0，而不是跳过方法

**方案2**：修改依赖检查逻辑
- 区分"运行设备"和"停机设备"
- 停机设备允许依赖数据为0

**方案3**：添加专门的停机设备计算方法
- 优先级最低
- 无依赖要求
- 直接返回0

## 📌 总结

### 核心发现

1. **三层过滤机制**：
   - 第一层：数据加载过滤（用户可控）
   - 第二层：计算阶段阈值过滤（硬编码，仅pump_flow_rate_method_a）
   - 第三层：方法选择依赖检查（最严格，影响所有方法）

2. **第三层过滤是主要失败点**：
   - 要求frequency/power/flow类指标的值 > 0
   - 停机设备的这些值都是0
   - 导致所有方法都被跳过

3. **用户修改mv_device_running_1s表无效的原因**：
   - 修改只影响第一层（数据加载）
   - 第三层（方法选择）仍然会过滤掉停机设备
   - 即使数据加载成功，方法选择也会失败

4. **设备2成功的原因**：
   - pump_active_power = 269.6 kW > 0 ✅
   - pump_frequency = 48.44 Hz > 0 ✅
   - 通过第三层依赖检查
   - 方法A被选中并成功计算

### 失败链条

```
停机设备（freq=0, power=0）
    ↓
第一层：数据加载 ✅（用户修改running=1）
    ↓
第三层：方法选择依赖检查 ❌（non_zero_count=0）
    ↓
所有方法被跳过
    ↓
返回None
    ↓
计算失败
```
