## 🎯 核心发现

### 发现1：两套独立的设备运行判断标准

**问题**：用户修改 `mv_device_running_1s.running=1` 后，停机设备的指标计算仍然失败

**根本原因**：系统使用了两套独立的判断标准

#### 标准1：数据加载阶段（用户可控）
- **位置**：`orchestrator.py:228-242`
- **判断依据**：`mv_device_running_1s.running = 1`
- **用户修改**：所有设备 `running=1`
- **结果**：✅ 设备1、4、5的数据成功加载（包括freq=0, power=0）

#### 标准2：计算阶段（硬编码，用户不可控）
- **位置**：`orchestrator.py:1676-1681`
- **判断依据**：`freq >= 3.0 Hz AND power >= 0.5 kW`
- **设备1、4、5状态**：freq=0, power=0
- **结果**：❌ 不满足阈值 → 权重为0 → 无法计算

**证据链**：
```
数据加载阶段:
  设备1: running=1 (用户修改) → 数据加载成功 ✅
  
计算阶段:
  设备1: freq=0 < 3.0, power=0 < 0.5 → valid_mask=False → weight=0 → share=NaN ❌
  
最终结果:
  pump_flow_rate = Q_total × share = 3344.907 × NaN = NaN ❌
```

### 发现2：设备3的pump_torque失败是由于pump_flow_rate值错误

**问题**：设备3只缺失pump_torque一个指标，其他指标都成功

**根本原因**：设备3的pump_flow_rate值严重错误，导致能量守恒检查失败

#### 数据验证
```
设备3的pump_flow_rate = 3344.907 m³/h (与主管流量完全相同！)
设备3的pump_active_power = 3.2 kW (实际值)

权重计算验证:
  设备2: weight = 269.6 × 48.44 = 13,059.42
  设备3: weight = 3.2 × 4.90 = 15.68
  设备6: weight = 197.76 × 45.07 = 8,912.48
  总和: 21,987.58

设备3的正确份额 = 15.68 / 21,987.58 = 0.071%
设备3的正确流量 = 3344.907 × 0.071% = 2.38 m³/h ✅

设备3的实际流量 = 3344.907 m³/h ❌ (错误！)
```

#### pump_torque失败的原因
```
使用错误的流量值计算:
  Q = 3344.907 m³/h (错误值，应该是2.38)
  H = 49.57 m
  n = 147.14 rpm
  
计算水力功率:
  P_shaft = 1000 × 9.80665 × (3344.907/3600) × 49.57 / 1000 = 451.3 kW
  
能量守恒检查:
  P_shaft (451.3 kW) >> P_in (3.2 kW) ❌ 违反能量守恒！
  
计算扭矩:
  T = 451.3 × 1000 / (2π × 147.14 / 60) = 29,285 N·m ❌ 异常大！
  
结论: 触发验证器的合理性检查，导致pump_torque计算失败
```

### 发现4：权重总和计算逻辑正确但可能存在时间点不一致问题

**验证结果**：
- ✅ mv_device_running_1s表数据正确（所有设备running=1）
- ✅ 权重总和SQL查询正确（返回设备1-6的数据）
- ✅ 权重总和应该是21,987.58（包含设备2、3、6）

**未解之谜**：
- ❓ 为什么设备3的pump_flow_rate=3344.907（100%份额）而不是2.38（0.071%份额）？
- ❓ 实际计算时的weight_totals是否真的是21,987.58？

**可能原因**：
1. 计算时间点不一致（设备3计算时，mv_device_running_1s表状态可能不同）
2. 批处理顺序问题（设备3先于设备2、6计算，导致权重总和只包含设备3）
3. 缓存或状态问题（使用了过期的权重总和）

### 发现5：其他计算方法的失败模式（新增）

**问题**：设备1缺失5个指标，是否都是依赖链断裂导致？

**答案**：不是！有两种不同的失败模式

#### 失败类型分类

| 指标 | 失败类型 | 根本原因 | 是否依赖链断裂 |
|------|---------|---------|---------------|
| pump_flow_rate | 阈值过滤失败 | freq=0, power=0不满足阈值条件 | ❌ 否（根源失败） |
| pump_speed | 零值过滤失败 | freq=0不满足f>0条件 | ❌ 否（独立失败） |
| pump_cumulative_flow | 依赖链断裂 | pump_flow_rate缺失 | ✅ 是 |
| pump_efficiency | 依赖链断裂 | pump_flow_rate缺失 | ✅ 是 |
| pump_torque | 依赖链断裂 | pump_flow_rate和pump_speed都缺失 | ✅ 是 |

**统计**：
- 根源失败：1个（pump_flow_rate）
- 独立失败：1个（pump_speed）
- 依赖链断裂：3个（60%）

**pump_speed的零值过滤逻辑**：
```python
# calculators.py:476
valid_mask = ~np.isnan(f) & (f > 0)  # freq=0被过滤
```

**设计意图**：
- 频率为0意味着电机停止，转速应该为0
- 但转速为0可能被误解为"数据缺失"
- 因此计算方法选择返回NaN，而不是0

### 发现6：mv_device_running_1s表的正确生成逻辑（新增）

**问题**：mv_device_running_1s表的running字段是如何生成的？

**答案**：基于电流/功率/频率阈值计算，不是基于device_running指标！

#### 生成流程

1. **调用存储过程**：`sp_refresh_mv_running_phase`
2. **调用函数**：`fn_running_state_1s(station_id, device_id, start_ts, end_ts)`
3. **读取阈值配置**：从 `device_running_thresholds` 表读取
4. **获取原始数据**：从 `fact_measurements` 表获取电流、功率、频率
5. **滞回逻辑判断**：
   - 开启条件：任一启用信号 ≥ 开启阈值
   - 关闭条件：所有启用信号 ≤ 关闭阈值
6. **写入结果**：写入 `mv_device_running_1s` 表

#### 设备1的判断逻辑

**阈值配置**：
```
enable_i = true   (启用电流判断)
enable_p = false  (禁用功率判断)
enable_f = false  (禁用频率判断)
i_on = 541.12 A   (电流开启阈值)
i_off = 265.28 A  (电流关闭阈值)
```

**实际数据**：
```
pump_current_a/b/c = 0 A
max_i = 0 A
```

**判断结果**：
```
on_hit = (true AND 0 >= 541.12) = false
off_hit = (NOT true OR 0 <= 265.28) = true
is_running = false
running = 0  ← 系统计算的正确结果
```

**用户修改**：
```
running = 1  ← 用户手动修改
```

**结论**：用户的修改覆盖了系统的计算结果，但只影响数据加载阶段，不影响计算阶段的硬编码阈值过滤。

### 发现7：三层过滤机制导致停机设备无法计算（新增）

**问题**：为什么用户修改mv_device_running_1s表后，停机设备仍然无法计算？

**答案**：系统有三层独立的过滤机制，用户只能控制第一层！

#### 三层过滤机制

**第一层：数据加载过滤**（orchestrator.py:228-242）
- 条件：`mv_device_running_1s.running = 1`
- 设备1：✅ 通过（用户手动修改running=1）
- 影响：控制哪些设备的数据被加载到内存
- 用户可控：✅ 是

**第二层：计算阶段阈值过滤**（orchestrator.py:1676-1681）
- 条件：`freq >= 3.0 Hz AND power >= 0.5 kW`
- 设备1：❌ 失败（freq=0, power=0）
- 影响：只在pump_flow_rate_method_a中生效
- 用户可控：❌ 否（硬编码）

**第三层：方法选择依赖检查**（method_selector.py:159-166）
- 条件：`frequency/power/flow类指标的值 > 0`
- 设备1：❌ 失败（power=0, freq=0）
- 影响：影响所有计算方法的选择
- 用户可控：❌ 否（代码逻辑）

#### 设备1的完整过滤流程

```
停机设备（freq=0, power=0）
    ↓
【第一层】数据加载过滤
    条件：mv_device_running_1s.running = 1
    结果：✅ 通过（用户修改）
    ↓
【第三层】方法选择依赖检查
    条件：frequency/power/flow > 0
    结果：❌ 失败（所有6个方法都被跳过）
    返回：None
    ↓
    计算失败
    ↓
【第二层】计算阶段阈值过滤
    ⚠️ 未执行（因为方法选择已失败）
```

**关键洞察**：
- 第三层过滤比第二层更早执行
- 第三层过滤更严格（要求 > 0，而不是 >= 3.0）
- 即使绕过第二层，第三层也会阻止计算
- 用户修改只能绕过第一层，无法绕过第三层

### 发现9：验证器的多层防护机制（新增）

**问题**：为什么设备3的pump_torque被拒绝？

**答案**：验证器的能量守恒检查成功捕获了计算错误！

#### 验证器的四层防护

**第一层：基本数值验证**
- NaN检查
- Inf检查
- 正数检查
- 范围检查

**第二层：物理规律验证**
- 效率范围（0-100%）
- 功率一致性（能量守恒）
- 扭矩一致性（T = P × 9549 / n）
- 转速一致性（n = f / f_rated × n_rated）

**第三层：合理性验证**
- 效率合理范围（30-95%）
- 额定值检查（不超过额定值的120%）
- 异常值检测（效率<10%或>98%）

**第四层：特性曲线验证**（可选）
- Q-H曲线验证（流量-扬程）
- Q-P曲线验证（流量-功率）
- Q-η曲线验证（流量-效率）

#### 设备3的pump_torque验证失败过程

**步骤1：计算扭矩**
```python
Q = 3344.907 m³/h  # 错误的流量（100%份额）
H = 49.57 m
P_hydraulic = 1000 × 9.80665 × 3344.907 × 49.57 / 3600000 = 451.3 kW
P_shaft = 451.3 / 0.85 = 530.9 kW
n = 147 rpm
T = 530.9 × 9549 / 147 = 34,500 N·m
```

**步骤2：验证扭矩**
```python
P_electric = 3.2 kW  # 实际电功率
T_expected = 3.2 × 9549 / 147 = 207.7 N·m

relative_error = |34,500 - 207.7| / 207.7 = 165.1 (16510%)
tolerance = 0.15 (15%)

relative_error > tolerance  # ❌ 失败！
```

**步骤3：验证失败**
```python
errors.append("扭矩不一致：1 个值与功率/转速不匹配，最大误差16510.0%")
mask = np.array([False])
is_valid = False
```

**验证器的价值**：
- ✅ 成功捕获计算错误
- ✅ 防止错误数据写入数据库
- ✅ 提供详细的错误信息
- ✅ 保护数据质量

### 发现10：批处理机制使用线程隔离和独立查询

**核心问题**：为什么设备3的pump_flow_rate可能得到错误的权重总和？

**批处理特性**：
- 每个线程创建独立的CalculationOrchestrator实例
- 智能并行策略（基于数据量自动选择串行/并行）
- 每个设备独立查询fact_measurements表

**可能的根本原因**：
- 并行计算时，设备3查询fact_measurements表时，设备2和设备6的数据尚未写入
- weight_totals是局部变量，每个线程独立
- 导致设备3的权重总和只包含设备3自己，份额=100%

### 发现11：6层参数优先级系统支持设备级定制

**核心问题**：如何为低负荷运行的设备（如设备3）配置特殊参数？

**6层参数优先级**（从低到高）：
1. 全局计算参数
2. 全局默认额定参数
3. 设备额定参数
4. 泵站级额定参数
5. 泵站级计算参数
6. 设备级计算参数（最高优先级）

**解决方案**：
```sql
-- 为设备3配置更低的阈值
INSERT INTO calculation_parameters (device_id, method_id, param_name, param_value)
VALUES
    (3, 'pump_flow_rate_method_a', 'f_thr', 0.5),  -- 降低频率阈值
    (3, 'pump_flow_rate_method_a', 'p_thr', 0.1);  -- 降低功率阈值
```

### 发现12：CalculationContext通过extra字段传递扩展信息

**核心问题**：running_count和device_type如何在各组件间传递？

**CalculationContext特性**：
- frozen=True（不可变，线程安全）
- extra字段支持任意扩展信息
- 通过适配层支持向后兼容

**传递流程**：
```
Orchestrator创建CalculationContext（包含extra）
    ↓
传递给MethodSelector
    ↓
适配为legacy_context（合并extra字段）
    ↓
在条件判断中使用running_count和device_type
```
