## 🔍 问题1：历史数据可用性限制

### 问题描述

**原计划问题**:
- sp_detect_device_type_simple和sp_detect_running_mode_simple都假设可以读取"最近7天"的历史数据
- 实际情况：无法保证所有设备都有7天的历史数据可用
- 缺少降级处理策略

**用户关注点**:
- 最少需要多少天数据？
- 如果数据不足如何降级处理？

---

### 解决方案

#### 1.1 最少数据要求

| 功能 | 最少数据要求 | 推荐数据量 | 理由 |
|------|-------------|-----------|------|
| 设备类型识别 | 3天 | 7天 | 需要足够样本计算频率变异系数 |
| 运行模式识别 | 3天 | 7天 | 需要足够样本计算运行时长比例 |
| 阈值学习 | 1天 | 7天 | 现有逻辑已支持，但样本越多越准确 |

#### 1.2 降级处理策略

```
数据充足度评估:
├─ 7天+ 数据 → 高质量识别 (threshold_quality='high')
│  └─ 使用完整算法，结果可靠
├─ 3-7天数据 → 中等质量识别 (threshold_quality='medium')
│  └─ 使用完整算法，结果基本可靠
├─ 1-3天数据 → 低质量识别 (threshold_quality='low')
│  └─ 使用保守策略，结果仅供参考
└─ <1天数据 → 无法识别 (threshold_quality='insufficient')
   └─ 使用默认值，等待数据积累
```

#### 1.3 新增字段

**字段名**: `data_days_available` (INTEGER)

**用途**: 记录实际可用数据天数，用于评估识别质量

**使用示例**:
```sql
-- 在sp_detect_device_type_simple中计算
SELECT 
    COUNT(DISTINCT DATE(ts_bucket)) AS data_days_available
FROM fact_measurements
WHERE device_id = p_device_id
  AND ts_bucket >= NOW() - INTERVAL '7 days'
  AND quality_status = 0;
```

#### 1.4 算法调整

**sp_detect_device_type_simple**:
```sql
-- 1. 计算data_days_available
-- 2. 根据data_days_available决定是否执行识别
IF data_days_available < 1 THEN
    device_type = 'unknown'
    threshold_quality = 'insufficient'
    RETURN
END IF

-- 3. 执行识别（使用可用数据）
-- 4. 根据data_days_available设置threshold_quality
IF data_days_available >= 7 THEN
    threshold_quality = 'high'
ELSIF data_days_available >= 3 THEN
    threshold_quality = 'medium'
ELSE
    threshold_quality = 'low'
END IF
```

**sp_detect_running_mode_simple**: 同样的逻辑

## 🔍 问题2：设备类型数据来源不明确

### 问题描述

**原计划问题**:
- 计划中提到通过频率变异系数(CV)自动识别设备类型
- 未考虑dim_devices表中已有pump_type字段
- 未说明如何与现有数据协同工作

**用户关注点**:
- dim_devices表中是否有device_type字段？
- 如果有，sp_detect_device_type_simple应该如何与现有数据协同工作？
- 是否应该支持"人工设置优先，自动识别作为fallback"的策略？

---

### 解决方案

#### 2.1 dim_devices表结构分析

**已有字段**:
```sql
CREATE TABLE dim_devices (
    id              BIGINT PRIMARY KEY,
    station_id      BIGINT NOT NULL,
    name            TEXT NOT NULL,
    type            TEXT NOT NULL,              -- 设备类型（pump/main_pipeline/clear_water_pool）
    pump_type       TEXT,                       -- 泵类型（variable_frequency/soft_start）
    extra           JSONB,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    is_active       BOOLEAN NOT NULL DEFAULT true
);
```

**关键发现**:
- ✅ `pump_type` 字段已存在
- ✅ 数据来源: `configs/dimensions.yaml` 配置文件
- ✅ 值域: 'variable_frequency' (变频泵) 或 'soft_start' (软启动泵)

#### 2.2 优先级策略

**策略**: "人工设置优先，自动识别作为fallback"

```
设备类型识别优先级:
1. 优先使用 dim_devices.pump_type（来自配置文件）
   ├─ 如果 pump_type = 'variable_frequency' → device_type = 'vfd'
   ├─ 如果 pump_type = 'soft_start' → device_type = 'soft_start'
   └─ device_type_source = 'config'

2. 如果 pump_type IS NULL，执行自动识别
   ├─ 基于频率变异系数(CV)识别
   └─ device_type_source = 'auto'

3. 如果数据不足，使用默认值
   └─ device_type = 'unknown', device_type_source = 'unknown'
```

#### 2.3 新增字段

**字段名**: `device_type_source` (TEXT)

**用途**: 记录设备类型的来源

**值域**: 
- 'config': 从dim_devices.pump_type读取
- 'auto': 自动识别
- 'unknown': 未识别

#### 2.4 算法调整

**sp_detect_device_type_simple修改**:
```sql
-- 步骤1: 读取dim_devices.pump_type
SELECT pump_type INTO v_pump_type
FROM dim_devices
WHERE id = p_device_id;

-- 步骤2: 如果pump_type不为NULL，直接使用
IF v_pump_type IS NOT NULL THEN
    v_device_type := CASE v_pump_type
        WHEN 'variable_frequency' THEN 'vfd'
        WHEN 'soft_start' THEN 'soft_start'
        ELSE 'unknown'
    END;
    v_device_type_source := 'config';
    v_device_type_auto_detected := FALSE;
    
    -- 根据device_type设置enable_f和权重
    IF v_device_type = 'vfd' THEN
        v_enable_f := TRUE;
        v_weight_current := 0.4;
        v_weight_power := 0.3;
        v_weight_frequency := 0.2;
    ELSIF v_device_type = 'soft_start' THEN
        v_enable_f := FALSE;
        v_weight_current := 0.6;
        v_weight_power := 0.4;
        v_weight_frequency := 0.0;
    END IF;
    
    -- 更新device_running_thresholds表
    UPDATE device_running_thresholds
    SET device_type = v_device_type,
        device_type_source = v_device_type_source,
        device_type_auto_detected = v_device_type_auto_detected,
        enable_f = v_enable_f,
        signal_weight_current = v_weight_current,
        signal_weight_power = v_weight_power,
        signal_weight_frequency = v_weight_frequency,
        updated_at = NOW(),
        updated_by = 'sp_detect_device_type_simple'
    WHERE device_id = p_device_id;
    
    RETURN;
END IF;

-- 步骤3: 如果pump_type为NULL，执行自动识别
-- （原有逻辑，设置device_type_source='auto'）
```

#### 2.5 数据迁移调整

**初始化时优先使用dim_devices.pump_type**:
```sql
UPDATE device_running_thresholds drt
SET 
    device_type = CASE 
        WHEN EXISTS (
            SELECT 1 FROM dim_devices d 
            WHERE d.id = drt.device_id 
              AND d.pump_type = 'variable_frequency'
        ) THEN 'vfd'
        WHEN EXISTS (
            SELECT 1 FROM dim_devices d 
            WHERE d.id = drt.device_id 
              AND d.pump_type = 'soft_start'
        ) THEN 'soft_start'
        ELSE 'unknown'
    END,
    device_type_source = CASE 
        WHEN EXISTS (
            SELECT 1 FROM dim_devices d 
            WHERE d.id = drt.device_id 
              AND d.pump_type IS NOT NULL
        ) THEN 'config'
        ELSE 'unknown'
    END
WHERE device_type IS NULL;
```

## 🔍 问题3：维度表ID变化的自适应处理

### 问题描述

**原计划问题**:
- 未考虑dim_devices和dim_stations表的ID可能会发生变化
- 未说明device_running_thresholds表如何自适应ID变化

**用户关注点**:
- device_running_thresholds表中的device_id必须能够自适应dim_devices表的ID变化
- 可能的解决方案：外键约束、自动更新、使用业务标识

---

### 解决方案

#### 3.1 当前系统状态分析

**关键发现**:
1. ✅ **dim_devices表使用固定ID**（从配置文件读取）
2. ✅ **已执行迁移脚本**: `scripts/sql/migration/migrate_dim_ids_to_fixed.sql`
3. ✅ **设备ID范围**: 1-8（固定不变）
4. ✅ **序列已删除**: `dim_devices_id_seq` 不存在
5. ❌ **外键约束缺失**: device_running_thresholds表没有外键约束

**代码证据**:
```python
# app/services/ingest/prepare_dim/__init__.py
def _upsert_device(cur, device_id: int, station_id: int, name: str, ...):
    """使用配置文件中的固定ID"""
    upsert_sql = """
        INSERT INTO public.dim_devices(id, station_id, name, type, pump_type)
        VALUES (%s, %s, %s, %s, %s)
        ON CONFLICT (id) DO UPDATE SET ...
    """
```

#### 3.2 外键约束策略

**必须添加外键约束**:
```sql
ALTER TABLE public.device_running_thresholds
ADD CONSTRAINT device_running_thresholds_device_id_fkey
FOREIGN KEY (device_id)
REFERENCES public.dim_devices(id)
ON UPDATE CASCADE
ON DELETE CASCADE;
```

**预期效果**:
- ✅ 如果device_id变化，device_running_thresholds表自动更新（CASCADE）
- ✅ 如果设备被删除，device_running_thresholds表自动清理（CASCADE）
- ✅ 防止孤立记录（device_id不存在于dim_devices表）

#### 3.3 风险评估

**风险等级**: **极低**

**理由**:
1. 当前系统使用固定ID，ID不会变化
2. 外键约束只是额外的安全保障
3. 即使未来ID变化，外键约束会自动处理
4. 已有多个表使用相同的外键约束策略（参考: dim_device_capabilities, device_rated_params等）

#### 3.4 实施步骤

**步骤1**: 检查孤立记录
```sql
SELECT COUNT(*) AS orphan_count
FROM public.device_running_thresholds drt
LEFT JOIN public.dim_devices d ON d.id = drt.device_id
WHERE d.id IS NULL;
```

**步骤2**: 如果orphan_count = 0，添加外键约束
```sql
ALTER TABLE public.device_running_thresholds
ADD CONSTRAINT device_running_thresholds_device_id_fkey
FOREIGN KEY (device_id)
REFERENCES public.dim_devices(id)
ON UPDATE CASCADE
ON DELETE CASCADE;
```

**步骤3**: 验证外键约束
```sql
SELECT constraint_name, update_rule, delete_rule
FROM information_schema.referential_constraints
WHERE constraint_name = 'device_running_thresholds_device_id_fkey';
```

## 🔍 问题4：与prepare_dim流程的兼容性

### 问题描述

**原计划问题**:
- 未说明如何与prepare_dim流程集成
- 未说明device_running_thresholds表在prepare_dim流程中的处理方式

**用户关注点**:
- device_running_thresholds表的数据在prepare_dim流程中应该如何处理？
- 阶段1的迁移脚本应该在prepare_dim流程的哪个阶段执行？
- 如何确保prepare_dim流程不会破坏device_running_thresholds表中已学习的参数？

---

### 解决方案

#### 4.1 prepare_dim流程概述

**流程图**:
```
prepare_dim流程:
├─ 阶段1（在merge-fact前执行）:
│  ├─ 1. 备份21个表（包括device_running_thresholds）
│  ├─ 2. 清空非备份表
│  ├─ 3. 重建维度表（dim_stations, dim_devices, dim_metric_config）
│  ├─ 4. 恢复手动配置表（9个表）
│  └─ 5. 重建基础配置表（dim_device_capabilities等，使用自适应SQL脚本）
│
└─ 阶段2（在merge-fact后执行）:
   ├─ 1. 清空规则表（device_running_thresholds等）
   ├─ 2. 生成规则表（调用sp_refresh_device_running_thresholds_*）
   └─ 3. 生成映射表
```

#### 4.2 device_running_thresholds表的分类

**表分类**: D类规则表（自适应SQL脚本生成）

**备份状态**: ✅ 已纳入prepare_dim备份机制

**恢复策略**: ❌ 不从备份恢复，而是重新生成

**代码证据**:
```python
# app/services/ingest/prepare_dim/__init__.py
tables_to_backup = [
    # ...
    # D类：规则表（6个）
    "metric_rule_auto_baseline",
    "metric_rule_auto_baseline_shadow",
    "metric_quality_rules",
    "metric_quality_rules_shadow",
    "device_running_thresholds",  # ← 在这里
    "device_running_thresholds_shadow",
]
```

#### 4.3 阶段1迁移脚本的执行时机

**执行时机**: prepare_dim阶段1完成后，手动执行一次

**执行步骤**:
```
1. 执行 prepare_dim 阶段1（重建维度表）
2. 手动执行 060_alter_device_running_thresholds_phase1.sql（添加新字段）
3. 手动执行 060_add_foreign_key_constraint.sql（添加外键约束）
4. 手动执行数据迁移SQL（初始化新字段）
5. 执行 prepare_dim 阶段2（重新生成规则表）
```

**理由**:
- prepare_dim阶段1会重建dim_devices表，必须先完成
- 添加外键约束前，必须确保dim_devices表已存在
- 数据迁移需要读取dim_devices.pump_type，必须在维度表重建后执行

#### 4.4 prepare_dim流程对device_running_thresholds表的处理

**阶段1**: 
- ✅ 备份device_running_thresholds表
- ❌ 不清空device_running_thresholds表（保持原有数据）
- ❌ 不恢复device_running_thresholds表（保持原有数据）

**阶段2**:
- ✅ 清空device_running_thresholds表
- ✅ 重新生成device_running_thresholds表（调用sp_refresh_device_running_thresholds_*）

**代码证据**:
```python
# app/services/ingest/prepare_dim/__init__.py
def _clear_non_backup_tables(cur):
    """清空非备份表，不清空device_running_thresholds"""
    # device_running_thresholds在backup_tables集合中，不会被清空
    pass
```

#### 4.5 新增字段的初始化

**初始化时机**: 在prepare_dim阶段2之前，手动执行一次

**初始化SQL**: 参见问题2的数据迁移调整

#### 4.6 兼容性保证

**保证措施**:
1. ✅ 不修改prepare_dim流程的代码
2. ✅ 不修改备份/恢复逻辑
3. ✅ 新增字段都有默认值，不影响现有查询
4. ✅ 外键约束不影响prepare_dim流程的清空/重建操作
5. ✅ 阶段1迁移脚本独立执行，不依赖prepare_dim流程
