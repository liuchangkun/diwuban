## 🎯 核心结论

### 问题的本质

**`mv_device_running_1s` 表的 `running` 字段只控制数据是否被加载，不控制数据是否参与计算。**

1. **数据加载阶段** (✅ 成功):
   - `filter_running=True` → JOIN `mv_device_running_1s` 表
   - `dr.running = 1` → 设备1的数据被加载
   - 结果: `pump_frequency=0`, `pump_active_power=0` 进入内存

2. **权重计算阶段** (❌ 失败):
   - 使用**阈值过滤**: `freq >= 3.0 Hz` AND `power >= 0.5 kW`
   - 设备1不满足阈值条件 → 权重为0
   - 权重为0 → `share = NaN`
   - `share = NaN` → 无法计算流量

3. **流量计算阶段** (❌ 失败):
   - `pump_flow_rate = main_pipeline_flow_rate × share`
   - `share = NaN` → `pump_flow_rate = NaN`
   - 结果未通过验证 → 不写入数据库

### 为什么设备2和6成功？

- 频率 > 3.0 Hz ✅
- 功率 > 0.5 kW ✅
- 权重 > 0 ✅
- 可以计算流量分摊 ✅

### 为什么设备3部分成功？

- 频率 = 4.90 Hz > 3.0 Hz ✅
- 功率 = 3.2 kW > 0.5 kW ✅
- `pump_flow_rate` 计算成功 ✅
- `pump_torque` 失败原因: 依赖的 `pump_speed` 过小或其他数值异常

### 验证3: 为什么设备3的torque失败？

**依赖分析**:
```
pump_torque_method_a:
  依赖: pump_flow_rate ✅, pump_head ✅, pump_speed ✅

pump_speed_method_a:
  依赖: pump_frequency ✅ (4.90 Hz)
  计算: n = (f / f_ref) × n_ref = (4.90 / 50.0) × 1500 = 147 rpm

pump_torque 计算:
  T = (ρ × g × Q × H / 1000) / (2π × n / 60) × 1000
  如果 n = 147 rpm 过小，可能导致数值异常
```

**🔥 重大发现：设备3的pump_flow_rate值严重错误！**

**数据验证**：
```sql
-- 设备3的pump_flow_rate
SELECT device_id, value, source_hint
FROM fact_measurements fm
JOIN dim_metric_config mc ON mc.id = fm.metric_id
WHERE ts_bucket = '2025-10-23 10:48:08+08'
  AND device_id = 3
  AND mc.metric_key = 'pump_flow_rate'

结果: value = 3344.907 m³/h (与主管流量完全相同！)
source_hint = calculation:pump_flow_rate_method_a
```

**权重计算验证**：
```
设备2: power=269.6 kW, freq=48.44 Hz → weight = 13,059.42
设备3: power=3.2 kW, freq=4.90 Hz → weight = 15.68
设备6: power=197.76 kW, freq=45.07 Hz → weight = 8,912.48
权重总和 = 21,987.58

设备2份额 = 13,059.42 / 21,987.58 = 59.4% → 流量 = 1,986.86 m³/h ✅
设备3份额 = 15.68 / 21,987.58 = 0.071% → 流量 = 2.38 m³/h ❌ (实际3,344.907)
设备6份额 = 8,912.48 / 21,987.58 = 40.5% → 流量 = 1,355.69 m³/h
```

**pump_torque失败的根本原因**：
```
设备3的pump_flow_rate = 3344.907 m³/h (错误值，应该是2.38)
设备3的pump_active_power = 3.2 kW (实际值)

计算水力功率:
  Q_m3s = 3344.907 / 3600 = 0.929 m³/s
  P_shaft = 1000 × 9.80665 × 0.929 × 49.57 / 1000 = 451.3 kW

能量守恒检查:
  P_shaft (451.3 kW) >> P_in (3.2 kW)  ❌ 违反能量守恒！

计算扭矩:
  omega = 2π × 147.14 / 60 = 15.41 rad/s
  T = 451.3 × 1000 / 15.41 = 29,285 N·m  ❌ 异常大！

结论: pump_flow_rate的错误值导致计算出的水力功率远超实际电功率，
      触发验证器的合理性检查，导致pump_torque计算失败。
```

**新问题：为什么设备3的pump_flow_rate计算错误？**
- 使用了pump_flow_rate_method_a（功率×频率分摊法）
- 权重计算应该正确（15.68）
- 但最终存储的值是主管流量（3344.907），而不是分摊后的流量（2.38）
- 这说明在权重分摊计算或结果存储环节存在BUG

**可能原因**:
1. `pump_speed` 计算结果过小（147 rpm）
2. 扭矩计算时出现数值溢出或除零
3. 验证器拒绝了异常值

## 🎯 最终答案

### 您的疑问：为什么修改 mv_device_running_1s 表后计算还是失败？

**答案**:

`mv_device_running_1s` 表的 `running` 字段**只控制数据加载**，不控制**计算逻辑**。

1. **数据加载阶段** (✅ 您的修改生效了):
   - `running=1` → 设备1的数据被加载到内存
   - 包括 `pump_frequency=0`, `pump_active_power=0`

2. **计算阶段** (❌ 这里失败了):
   - 计算引擎使用**硬编码的阈值**判断数据有效性
   - `freq >= 3.0 Hz` AND `power >= 0.5 kW`
   - 设备1不满足阈值 → 权重为0 → 无法计算

3. **根本原因**:
   - **两套判断标准不一致**:
     * 数据加载: 基于 `mv_device_running_1s.running` (您可以控制)
     * 计算逻辑: 基于硬编码阈值 `f_thr=3.0, p_thr=0.5` (您无法通过修改表控制)

4. **为什么设计成这样**:
   - 停机设备的频率和功率都是0
   - 如果允许0值参与计算，会导致数学错误（除零、权重为0等）
   - 阈值过滤是为了保证计算的数值稳定性
