## 🔍 详细分析

### 表1: device_rated_params（设备额定参数）

**处理方式**: ❌ **不从备份恢复，完全重新生成**

**流程**:
```
1. 备份（prepare-dim步骤1）
   └─ BackupManager.backup_tables() 备份到 backups/device_rated_params/

2. 清空（prepare-dim步骤2）
   └─ DELETE FROM device_rated_params

3. 重建维度表（prepare-dim步骤3）
   └─ 从Excel导入 dim_stations 和 dim_devices

4. 执行自适应SQL脚本（prepare-dim步骤4）
   └─ 执行 scripts/sql/adaptive/02_device_related.sql
      ├─ TRUNCATE TABLE device_rated_params CASCADE
      └─ INSERT INTO device_rated_params (device_id, ...)
         SELECT d.id, ... FROM dim_devices d
         JOIN dim_stations s ON d.station_id = s.id
         WHERE s.name = '二期供水泵房' AND d.name = '二期供水泵房1#泵'

5. 不恢复备份（prepare-dim步骤5）
   └─ device_rated_params 不在 manual_config_tables 列表中
```

**为什么不恢复备份？**
- ✅ **设备ID可能变化**: 备份中的device_id可能与新导入的dim_devices不一致
- ✅ **自适应关联**: 使用 `station_name + device_name` 定位设备，适应设备ID变化
- ✅ **完全重建**: 确保参数与当前设备完全对应

**数据来源**: `scripts/sql/adaptive/02_device_related.sql`

## 🎯 关键洞察

### 1. 为什么有些表备份了却不恢复？

**原因**: 这些表依赖设备ID，而设备ID在每次prepare-dim时可能变化。

**示例**:
```
第一次prepare-dim:
- 设备 "二期供水泵房1#泵" → device_id = 1
- device_rated_params: (device_id=1, param_key='rated_flow', value_numeric=400)

第二次prepare-dim（重新导入Excel）:
- 设备 "二期供水泵房1#泵" → device_id = 10（ID变化！）
- 如果恢复备份 → device_id=1 无效（外键约束失败）
- 如果重新生成 → device_id=10 正确（自适应关联）
```

### 2. 自适应SQL脚本的优势

**传统方式**（硬编码device_id）:
```sql
INSERT INTO device_rated_params (device_id, param_key, value_numeric)
VALUES (1, 'rated_flow', 400);  -- device_id=1 硬编码
```

**自适应方式**（使用station_name + device_name）:
```sql
INSERT INTO device_rated_params (device_id, param_key, value_numeric)
SELECT d.id, 'rated_flow', 400
FROM dim_devices d
JOIN dim_stations s ON d.station_id = s.id
WHERE s.name = '二期供水泵房' AND d.name = '二期供水泵房1#泵';
-- device_id 自动适应
```

**优势**:
- ✅ 适应设备ID变化
- ✅ 适应设备增减
- ✅ 适应站点重组
- ✅ 提高系统鲁棒性

### 3. 备份的双重作用

**作用1：数据恢复**（主要用于手动配置表）
- calculation_validation_config: 恢复人工配置的验证规则

**作用2：数据审计**（主要用于自动生成表）
- device_rated_params: 追溯参数变化历史
- calculation_parameters: 追溯参数变化历史
- metric_quality_rules: 追溯规则变化历史
