## 📋 需求概述（详细版）

实现一个完整的缺失指标计算系统，利用已有的数据指标，通过多种计算方法计算出缺失的指标，并通过机理验证和特性曲线验证确保结果的准确性。

### 核心目标（SMART原则）
1. **自动识别缺失指标**：100%覆盖metrics_presence_per_second_device中的need_compute_metrics
2. **智能选择计算方法**：每个指标支持3-6种计算方法，自动选择最优方法
3. **高性能批量计算**：单设备单小时数据处理时间 < 10秒（目标）
4. **多层验证机制**：验证通过率 > 90%（目标）
5. **参数自动优化**：RMS误差 < 10%（目标）

## 🔍 已有基础设施梳理

### 1. 数据库基础设施

#### 核心数据表
- **fact_measurements**: TimescaleDB Hypertable，存储所有测量数据
  - 字段：station_id, device_id, metric_key, ts_bucket, value, quality_status, quality_codes
  - 已有索引和分区优化
  
- **dim_metric_config**: 指标配置表
  - 存储所有指标的元数据（名称、单位、分类等）
  
- **metric_capability_policy**: 指标能力策略表
  - 字段：metric_key, acquisition_status, compute_flag
  - 标记哪些指标可以采集、哪些需要计算
  
- **metrics_presence_per_second_device**: 指标存在性表
  - 字段：station_id, device_id, ts_second, available_metrics[], need_compute_metrics[]
  - 记录每秒每设备的可用/缺失指标
  
- **mv_device_running_1s**: 设备运行状态物化视图
  - 用于过滤运行状态数据

#### 数据库函数
- **get_station_devices_metrics_by_time_range**: 获取泵站级时间对齐数据
- **get_device_metrics_by_time_range**: 获取设备级时间对齐数据

### 2. 计算公式文档

**docs/计算原理和公式.md** 包含详细的计算方法：

#### 需要计算的指标
1. **pump_flow_rate** (泵瞬时流量) - 6种方案
   - A: 功率×频率分摊（首选）
   - B: 累计量求导
   - C: 单泵运行直接取总管流量
   - D: 仅功率分摊
   - E: 仅频率分摊
   - F: 数据驱动回归融合

2. **pump_outlet_pressure** (泵出口压力) - 4种方案
   - A: 直接读取
   - B: 以总管出口压力代替
   - C: 由进口压力与扬程回推
   - D: 泵组层面近似

3. **pump_head** (泵扬程) - 1种主要方案
   - 基于进出口压差计算

4. **pump_efficiency** (泵效率) - 1种主要方案
   - 基于功率、流量、扬程计算

5. **pump_speed** (泵转速) - 3种方案
   - A: 相对转速
   - B: 绝对转速（基于极数）
   - C: 一次性标定n-f关系

6. **pump_torque** (泵扭矩) - 2种方案
   - A: 由水力功率与转速
   - B: 由电功率与频率

#### 指标依赖关系
```
pump_efficiency → pump_flow_rate, pump_head, pump_active_power
pump_torque → pump_flow_rate, pump_head, pump_speed
pump_outlet_pressure(方案C) → pump_head, pump_inlet_pressure
pump_head → pump_outlet_pressure, pump_inlet_pressure
```

## 🎯 缺失部分识别

### 需要新建的数据库表

1. **metric_calculation_order** - 指标计算顺序表
   - metric_key, depends_on[], priority, order_index
   
2. **calculation_method_registry** - 计算方法注册表
   - method_id, metric_key, method_name, priority, conditions, formula_ref
   
3. **calculation_parameters** - 计算参数表
   - station_id, device_id, metric_key, method_id, param_name, param_value
   
4. **calculation_validation_config** - 验证配置表
   - station_id, device_id, metric_key, validator_type, param_name, param_value
   
5. **calculation_failures_log** - 计算失败日志表
   - station_id, device_id, metric_key, ts_second, method_id, error_type, error_message
   
6. **optimization_history** - 优化历史表
   - station_id, device_id, metric_key, optimization_type, params_before, params_after, improvement_score

### 需要实现的模块

1. **指标依赖分析器** (Dependency Analyzer)
   - 解析计算方法的依赖关系
   - 生成拓扑排序的计算顺序
   
2. **计算方法选择器** (Method Selector)
   - 根据可用指标和运行状态选择最佳方法
   - 支持优先级和条件匹配
   
3. **指标计算引擎** (Calculation Engine)
   - 每个指标的计算函数实现
   - 支持向量化计算
   
4. **结果验证器** (Validator)
   - 机理验证（物理定律、专业公式）
   - 特性曲线验证
   
5. **参数优化器** (Optimizer)
   - RLS递推最小二乘
   - 特性曲线优化
   
6. **批处理协调器** (Batch Coordinator)
   - 时间窗口管理
   - 并行任务调度
   - 批量写入优化

## 💡 技术架构理解

### 工作流程
```
1. 读取metrics_presence_per_second_device
   ↓
2. 依赖分析 → 生成计算顺序
   ↓
3. 方法选择 → 选择最佳计算方法
   ↓
4. 数据获取 → 获取所需数据（过滤质量、运行状态）
   ↓
5. 执行计算 → 调用计算函数
   ↓
6. 结果验证 → 机理验证 + 曲线验证
   ↓
7. 写入数据 → 批量写入fact_measurements
   ↓
8. 更新presence → 更新metrics_presence_per_second_device
   ↓
9. 循环迭代 → 直到所有缺失指标计算完成
```

### 性能考虑
- 数据量非常大，需要分批处理
- 支持按设备、按指标、按时间段并行
- 批量大小根据性能自动调整
- 使用TimescaleDB的时间分区优化

## 📊 复杂度评估

### 高复杂度因素
1. **指标依赖关系复杂**: 需要拓扑排序，可能存在循环依赖
2. **计算方法多样**: 每个指标多种方法，需要智能选择
3. **验证机制复杂**: 多层验证，需要大量领域知识
4. **性能要求高**: 大数据量下的实时计算
5. **参数优化困难**: RLS和曲线优化需要数学算法支持

### 风险点
1. **数据一致性**: 并发计算可能导致冲突
2. **计算精度**: 累积误差可能影响后续计算
3. **性能瓶颈**: 数据库I/O可能成为瓶颈
4. **扩展性**: 新增指标需要修改多处代码
