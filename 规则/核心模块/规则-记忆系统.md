# 记忆系统原则

## 概述

记忆系统是AI工作的"长期知识库"，用于积累和复用项目知识，避免重复劳动和知识遗忘。

---

## 记忆分层结构

记忆按以下层次组织，每层有不同的更新频率和优先级：

### 1. 规则层（最高优先级）

- **实体类型**：`项目规则`、`编码规范`、`质量标准`、`数据库规范`、`架构约束`
- **规则文档**：
  * `.memory/规则层/项目规则.md` - 项目级强制规则（最高优先级）
  * `.memory/规则层/编码规范.md` - 详细的编码规范（注释、日志、命名、格式、错误处理、六大设计原则）
  * `.memory/规则层/质量标准.md` - 质量标准（代码质量、测试、文档、审查、性能）
  * `.memory/规则层/数据库规范.md` - 数据库规范（连接管理、查询优化、事务处理、命名规范、注释规范）
- **示例**：数据库配置严格限制在YAML文件、禁止使用代码占位符、单文件不超过600行
- **更新频率**：低（仅在规则变更时）
- **用途**：计划模式和审查模式的强制验证

### 2. 架构层

- **实体类型**：`项目`、`模块`、`服务`、`中间件`
- **示例**：FastAPI应用、数据库连接池、API路由系统
- **更新频率**：中（架构演进时）
- **用途**：研究模式的整体理解

### 3. 数据层

- **实体类型**：`数据表`、`视图`、`索引`、`Schema`
- **示例**：fact_measurements表结构、reporting schema
- **更新频率**：中（数据模型变更时）
- **用途**：研究模式和计划模式的数据建模

### 4. 代码层

- **实体类型**：`函数`、`类`、`接口`、`API端点`
- **示例**：get_device_metrics_by_time_range函数签名
- **更新频率**：高（每次代码变更）
- **用途**：执行模式的代码复用和审查模式的验证

### 5. 业务层

- **实体类型**：`业务流程`、`算法`、`计算逻辑`、`质量检查`
- **示例**：数据导入流程、特性曲线拟合算法
- **更新频率**：中（业务逻辑变更时）
- **用途**：创新模式的方案参考

## 记忆操作原则

- **主动检索**：每个模式开始前，必须自动检索相关记忆
- **自动更新**：每个模式结束时，必须自动更新知识图谱
- **质量优先**：只记录确认正确的信息，错误信息必须删除
- **去重合并**：更新前检查是否存在相似观察，避免冗余
- **版本演进**：架构变更时更新实体，而非创建重复实体
- **可追溯性**：所有记忆更新必须记录到任务文件的"记忆更新日志"

## 记忆查询策略

根据任务类型使用不同的查询关键词：

| 任务类型 | 查询关键词示例 | 预期检索内容 |
|---------|--------------|-------------|
| 新功能开发 | "功能模块"、"类似功能"、"依赖服务" | 相关服务、可复用代码、依赖关系 |
| Bug修复 | "相关函数"、"历史问题"、"质量规则" | 函数实现、已知问题模式、验证规则 |
| 性能优化 | "性能瓶颈"、"优化历史"、"索引策略" | 慢查询、优化方案、数据库索引 |
| 重构 | "代码结构"、"依赖关系"、"测试覆盖" | 模块依赖、影响范围、测试用例 |
| 数据建模 | "表结构"、"字段定义"、"外键关系" | 数据表、字段类型、关联关系 |

## 记忆质量控制

- **防止污染**：审查模式发现错误时，必须删除错误记忆
- **回滚机制**：用户反馈"失败"时，回滚本次任务的记忆更新
- **优先级规则**：项目规则 > 架构信息 > 代码实现；最新信息 > 历史信息
- **废弃标记**：过时的架构或代码应标记为"已废弃"而非删除

## 记忆验证原则

### 核心原则

**记忆是辅助，代码是真相。**

记忆系统可能因为以下原因不准确：
- 代码已变更但记忆未更新
- 数据库结构已演进但记忆滞后
- 用户手动修改了代码但未通知AI

因此，在关键节点必须验证记忆的准确性。

### 强制验证点

| 模式 | 验证时机 | 验证内容 | 验证方法 |
|------|---------|---------|---------|
| 研究 | 记忆检索后 | 关键文件是否存在 | 使用 view 工具读取文件 |
| 研究 | 记忆检索后 | 表结构是否一致 | 使用 query_PostgreSQL 查询 |
| 计划 | 制定计划前 | 函数签名是否准确 | 使用 view 工具查看函数定义 |
| 计划 | 制定计划前 | 项目规则是否最新 | 读取 `.memory/规则层/项目规则.md` |
| 执行 | 实施代码前 | 要调用的代码是否存在 | 使用 view 工具验证 |
| 执行 | 实施代码前 | 数据表字段是否存在 | 使用 query_PostgreSQL 验证 |
| 审查 | 验证实施前 | 实际规则文档内容 | 读取 `.memory/规则层/` 下所有规则 |

### 验证失败处理

当验证发现记忆与实际不符时：

1. **立即警告用户**：
   ```
   ⚠️ 记忆验证失败：
   - 记忆中：函数签名为 foo(a: int, b: str)
   - 实际代码：函数签名为 foo(a: int, b: str, c: bool = False)
   - 将更新记忆并继续执行
   ```

2. **更新记忆**：
   - 使用 add_observations_Memory 更新实体
   - 同时更新对应的文档文件

3. **记录到任务文件**：
   ```markdown
   ## 记忆验证失败记录
   - [日期时间] 函数foo签名不一致，已更新
   ```

## 双轨制记忆策略

项目使用**双轨制记忆系统**，结合知识图谱和文档化记忆的优势：

### 轨道1：知识图谱（Memory工具）

**用途**：快速检索和关系查询

**优势**：
- 支持复杂的关系查询（如"查找所有使用X的服务"）
- 支持语义搜索
- 运行时动态更新

**存储内容**：
- 实体：名称、类型、简要观察
- 关系：实体间的连接
- 结构化信息

**更新时机**：
- 每个模式结束时自动更新
- 发现新实体或关系时立即更新

### 轨道2：文档化记忆（.memory目录）

**用途**：人类可读和版本控制

**优势**：
- 可被Git版本控制
- 人类可直接编辑和审查
- 包含详细描述和示例
- 支持Markdown格式化

**存储内容**：
- 详细的表结构、字段说明
- 完整的函数签名和用途
- 技术决策的背景和理由
- 代码示例和使用说明

**更新时机**：
- 每个模式结束时同步更新
- 用户可手动编辑

### 同步策略

**AI的职责**：
1. 每次更新知识图谱时，同时更新对应的文档
2. 每次读取规则时，优先读取文档而非记忆
3. 发现文档与图谱不一致时，以文档为准

**更新流程**：
```
1. AI完成某个模式
2. 更新知识图谱（create_entities_Memory等）
3. 同时更新对应的文档文件（str-replace-editor）
4. 在任务文件中记录两处更新
```

### 使用优先级

| 场景 | 优先使用 | 理由 |
|------|---------|------|
| 快速检索相关实体 | 知识图谱 | 支持语义搜索和关系查询 |
| 查看详细函数签名 | 文档 | 包含完整参数说明和示例 |
| 验证项目规则 | 文档 | 用户维护，最权威 |
| 追踪依赖关系 | 知识图谱 | 关系查询更高效 |
| 查看技术决策背景 | 文档 | 包含详细的上下文 |
| 代码复用参考 | 文档 | 包含代码示例 |
