# 记忆管理指南

## 记忆实体类型定义

所有记忆实体必须使用以下标准化类型：

| 实体类型 | 用途 | 示例 |
|---------|------|------|
| 项目 | 顶层项目或子项目 | 泵站数据优化系统 |
| 模块 | 功能模块或子系统 | 数据导入模块、质量控制模块 |
| 服务 | 业务服务或技术服务 | 数据导入服务、特性曲线拟合服务 |
| 数据表 | 数据库表 | fact_measurements、dim_stations |
| 视图 | 数据库视图或物化视图 | mv_measurements_hourly |
| Schema | 数据库Schema | reporting、api |
| 函数 | 数据库函数或应用函数 | get_device_metrics_by_time_range |
| 类 | 应用层类 | DatabasePool、DataImporter |
| 接口 | API接口或抽象接口 | /api/v1/data/import |
| 中间件 | 应用中间件 | CORS中间件、请求日志中间件 |
| 算法 | 业务算法或计算逻辑 | 自动基线计算、特性曲线拟合 |
| 业务流程 | 端到端业务流程 | 数据导入流程、质量控制流程 |
| 项目规则 | 项目级强制规则 | 数据库配置严格限制在YAML文件 |
| 编码规范 | 代码风格和规范 | 所有注释使用中文 |
| 质量标准 | 质量检查标准 | 所有API必须包含错误处理 |
| 配置项 | 系统配置 | 数据库连接池配置 |

## 记忆关系类型定义

所有记忆关系必须使用以下标准化类型（主动语态）：

| 关系类型 | 含义 | 示例 |
|---------|------|------|
| 使用 | A使用B的功能或服务 | FastAPI应用 --使用--> 数据库连接池 |
| 调用 | A调用B的函数或接口 | 数据导入服务 --调用--> upsert_measurement |
| 依赖 | A依赖B才能运行 | 质量控制服务 --依赖--> fact_measurements |
| 包含 | A包含B作为子组件 | 数据导入模块 --包含--> CSV解析器 |
| 属于 | A属于B的一部分 | dim_devices --属于--> dim_stations |
| 关联 | A与B有业务关联 | fact_measurements --关联--> dim_metric_config |
| 实现 | A实现B的接口或规范 | DataImporter --实现--> IDataSource |
| 继承 | A继承B的类或接口 | CustomException --继承--> Exception |
| 写入数据到 | A向B写入数据 | 数据导入服务 --写入数据到--> fact_measurements |
| 读取数据从 | A从B读取数据 | API路由 --读取数据从--> reporting schema |
| 验证 | A验证B的数据或逻辑 | 质量控制服务 --验证--> fact_measurements |
| 聚合数据 | A聚合B的数据 | mv_measurements_hourly --聚合数据--> fact_measurements |
| 触发 | A触发B的执行 | 数据导入完成 --触发--> 质量控制 |

## 记忆观察编写规范

每条观察必须遵循以下规范：

### 规范要求

1. **简洁性**：单句描述，不超过100字
2. **准确性**：基于确认的事实，避免推测
3. **时效性**：描述当前状态，过时信息应删除
4. **独立性**：每条观察独立完整，不依赖其他观察
5. **可验证性**：可通过代码或文档验证

### 良好示例

- ✅ "TimescaleDB Hypertable，按 ts_bucket 时间分区，device_id 空间分区"
- ✅ "支持 CSV 文件自动编码检测（UTF-8、GBK）"
- ✅ "使用 psycopg3 作为 PostgreSQL 驱动"
- ✅ "函数签名：get_data(start: datetime, end: datetime) -> List[Dict]"
- ✅ "包含字段：id, name, created_at, updated_at"

### 不良示例

- ❌ "这个表很重要，存储了很多数据"（不具体）
- ❌ "可能使用了某种优化技术"（不确定）
- ❌ "详见第123行代码"（不独立）
- ❌ "这个函数很复杂，有很多参数"（不准确）
- ❌ "应该添加索引来优化性能"（推测，非事实）

## 记忆操作最佳实践

### 创建实体

**使用场景**：发现新的架构组件、函数、类、表等

**操作**：
```javascript
create_entities_Memory({
  entities: [
    {
      name: "get_user_data",
      entityType: "函数",
      observations: [
        "函数签名：get_user_data(user_id: int) -> Dict",
        "从数据库查询用户数据",
        "包含错误处理和日志记录"
      ]
    }
  ]
})
```

**注意事项**：
- 确保实体名称唯一且描述性强
- 使用标准化的实体类型
- 观察应该简洁、准确、独立

### 更新实体

**使用场景**：补充已有实体的新信息

**操作**：
```javascript
add_observations_Memory({
  observations: [
    {
      entityName: "get_user_data",
      contents: [
        "新增参数：include_deleted: bool = False",
        "支持查询已删除的用户"
      ]
    }
  ]
})
```

**注意事项**：
- 检查是否存在相似观察，避免冗余
- 如果信息已过时，先删除旧观察再添加新观察

### 创建关系

**使用场景**：记录实体间的依赖、调用、关联等关系

**操作**：
```javascript
create_relations_Memory({
  relations: [
    {
      from: "用户服务",
      to: "get_user_data",
      relationType: "调用"
    }
  ]
})
```

**注意事项**：
- 使用标准化的关系类型
- 关系应该是主动语态
- 确保关系的方向正确

### 删除观察

**使用场景**：发现错误或过时的信息

**操作**：
```javascript
delete_observations_Memory({
  deletions: [
    {
      entityName: "get_user_data",
      observations: [
        "函数签名：get_user_data(user_id: int) -> Dict"  // 旧的错误签名
      ]
    }
  ]
})
```

**注意事项**：
- 删除后立即添加正确的观察
- 在任务文件中记录删除原因

### 删除实体

**使用场景**：实体已被删除或废弃

**操作**：
```javascript
delete_entities_Memory({
  entityNames: ["old_function_name"]
})
```

**注意事项**：
- 谨慎使用，通常应该标记为"已废弃"而非删除
- 删除实体会同时删除所有相关关系

## 记忆同步策略

### 知识图谱 + 文档双轨制

**每次更新记忆时，必须同时更新两处**：

1. **更新知识图谱**（使用 Memory 工具）
2. **更新对应文档**（使用 str-replace-editor）

**示例流程**：
```
1. 发现新函数 get_user_data
2. 使用 create_entities_Memory 创建实体
3. 使用 str-replace-editor 更新 .memory/代码层/应用函数清单.md
4. 在任务文件中记录两处更新
```

### 文档格式示例

**应用函数清单.md**：
```markdown
## get_user_data

**类型**：函数

**文件**：`app/services/user.py`

**签名**：
```python
def get_user_data(user_id: int, include_deleted: bool = False) -> Dict
```

**用途**：从数据库查询用户数据

**参数**：
- `user_id`: 用户ID
- `include_deleted`: 是否包含已删除的用户，默认False

**返回值**：用户数据字典

**特性**：
- 包含错误处理和日志记录
- 支持查询已删除的用户

**依赖**：
- 数据库连接池
- users 表

**调用者**：
- 用户服务
- API路由

**最后更新**：2025-09-30
```
