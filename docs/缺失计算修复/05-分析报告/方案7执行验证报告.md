## 🎯 修复目标

### 问题描述

**具体表现**：
- 所有外键约束的UPDATE规则都是`NO ACTION`
- 如果维度表ID变化（如重新导入数据），依赖表的ID不会自动更新
- 会导致外键约束违反和数据不一致

**根本原因**：
- 创建外键约束时未指定`ON UPDATE CASCADE`
- 默认使用`NO ACTION`规则

**影响范围**：
- 23个表有外键约束但缺少级联更新
- 7个核心业务表缺少外键约束
- 如果重新导入维度表数据，会导致严重问题

### 修复目标

1. **为所有现有外键添加级联更新规则**：`ON UPDATE CASCADE`
2. **为缺少外键约束的核心业务表添加约束**
3. **确保数据一致性**：维度表ID变化时自动更新依赖表
4. **清理孤立数据**：确保数据完整性

## 📈 技术分析

### 级联更新机制

**工作原理**：
- 当维度表（如dim_devices）的ID发生变化时
- PostgreSQL自动更新所有引用该ID的依赖表
- 确保数据一致性，无需业务代码干预

**示例**：
```sql
-- 假设修改设备ID
UPDATE dim_devices SET id = 9999 WHERE id = 153;

-- 以下表的device_id会自动更新为9999：
-- - calculation_parameters
-- - device_rated_params
-- - completion_runs
-- - completion_steps
-- - device_running_thresholds_shadow
-- - dim_device_capabilities
-- - dim_metric_metadata_override
-- - metric_quality_rules_shadow
-- - metric_rule_auto_baseline_shadow
-- - calculation_failures_log
-- - calculation_performance_metrics
-- - calculation_validation_config
-- - optimization_history
-- - pump_characteristic_curves
-- - quality_diagnosis_log
-- - quality_profile_log
```

### 性能影响

**级联更新的性能开销**：
- 级联更新会触发多个表的更新操作
- 在大数据量场景下可能导致性能问题

**缓解措施**：
- 在维护窗口执行ID变化操作
- 使用事务确保原子性
- 监控执行时间，如果超过阈值则回滚

### 数据完整性提升

**外键约束的作用**：
- 确保引用完整性：依赖表的device_id必须存在于dim_devices表中
- 防止孤立数据：删除设备时自动删除相关数据（ON DELETE CASCADE）
- 自动维护一致性：修改设备ID时自动更新相关数据（ON UPDATE CASCADE）
