## 1. 设计目标

### 1.1 核心目标

1. **替代Redis**：使用内存缓存完全替代Redis缓存
2. **无外部依赖**：不依赖Redis、Memcached等外部服务
3. **性能优秀**：缓存命中率高，访问延迟低
4. **线程安全**：支持多线程并发访问
5. **自动过期**：支持TTL（Time To Live）机制
6. **易于维护**：代码简单，配置灵活

### 1.2 适用场景

- **单机部署**：不需要分布式缓存
- **任务量适中**：不需要Redis的高并发能力
- **环境限制**：无法使用Redis

---

## 2. 方案选择

### 2.1 方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| **functools.lru_cache** | 内置库，无需依赖，简单高效 | 无TTL，缓存不会自动过期 | 静态数据缓存（如方法注册信息） |
| **cachetools.TTLCache** | 支持TTL，自动过期，线程安全 | 需要额外依赖 | 动态数据缓存（如参数、计算结果） |
| **自定义缓存类** | 完全可控，可定制 | 开发成本高，需要测试 | 特殊需求（如LFU、自定义过期策略） |

### 2.2 推荐方案

**组合方案**：
- **静态数据**：使用 `functools.lru_cache`
- **动态数据**：使用 `cachetools.TTLCache`

**理由**：
- 成熟稳定，经过大量生产环境验证
- 性能优秀，满足单机部署需求
- 维护成本低，代码简洁
- 线程安全，无需额外加锁

## 3. 详细设计

### 3.1 方法注册信息缓存（静态数据）

**使用场景**：
- 缓存 `calculation_method_registry` 表的查询结果
- 数据变化频率低（方法注册信息很少变化）
- 需要高性能访问

**实现方案**：使用 `functools.lru_cache`

**代码示例**：
```python
from functools import lru_cache
from typing import List, Dict

@lru_cache(maxsize=128)
def get_methods_for_metric_cached(metric_key: str) -> tuple:
    """
    缓存方法查询结果
    
    注意：返回tuple而非list，因为lru_cache要求返回值可哈希
    """
    from app.adapters.db import get_connection
    
    query = """
        SELECT method_id, priority, dependencies, conditions, accuracy_level
        FROM calculation_method_registry
        WHERE metric_key = %s AND is_enabled = true
        ORDER BY priority DESC
    """
    
    with get_connection() as conn:
        with conn.cursor() as cur:
            cur.execute(query, (metric_key,))
            results = cur.fetchall()
    
    # 转换为tuple以支持缓存
    return tuple(
        {
            'method_id': row[0],
            'priority': row[1],
            'dependencies': row[2],
            'conditions': row[3],
            'accuracy_level': row[4]
        }
        for row in results
    )


def get_methods_for_metric(metric_key: str) -> List[Dict]:
    """
    获取指标的计算方法（带缓存）
    """
    # 调用缓存版本，转换回list
    cached_results = get_methods_for_metric_cached(metric_key)
    return list(cached_results)
```

**配置参数**：
- `maxsize=128`：最多缓存128个不同的metric_key
- LRU策略：最近最少使用的缓存项会被淘汰

**缓存失效**：
- 自动失效：进程重启时缓存清空
- 手动失效：调用 `get_methods_for_metric_cached.cache_clear()`

### 3.2 计算参数缓存（动态数据）

**使用场景**：
- 缓存 `calculation_parameters` 表的查询结果
- 数据变化频率中等（参数可能被优化或手动修改）
- 需要自动过期（避免使用过期参数）

**实现方案**：使用 `cachetools.TTLCache`

**代码示例**：
```python
from cachetools import TTLCache, cached
from cachetools.keys import hashkey
import threading

# 创建TTL缓存（5分钟过期）
_param_cache = TTLCache(maxsize=1000, ttl=300)
_param_cache_lock = threading.RLock()


@cached(cache=_param_cache, lock=_param_cache_lock, 
        key=lambda method_id, device_id: hashkey(method_id, device_id or 0))
def load_parameters_cached(method_id: str, device_id: int = None) -> Dict[str, float]:
    """
    加载计算参数（带缓存）
    
    缓存策略：
    - 最大缓存1000个参数集
    - TTL=5分钟（参数更新后5分钟内生效）
    - 线程安全
    """
    from app.adapters.db import get_connection
    
    query = """
        SELECT param_name, param_value
        FROM calculation_parameters
        WHERE method_id = %s AND (device_id = %s OR device_id IS NULL)
        ORDER BY device_id DESC NULLS LAST
    """
    
    with get_connection() as conn:
        with conn.cursor() as cur:
            cur.execute(query, (method_id, device_id))
            results = cur.fetchall()
    
    return {row[0]: row[1] for row in results}
```

**配置参数**：
- `maxsize=1000`：最多缓存1000个参数集
- `ttl=300`：缓存5分钟后自动过期
- `lock=threading.RLock()`：线程安全

**缓存失效**：
- 自动失效：5分钟后自动过期
- 手动失效：调用 `_param_cache.clear()`

### 3.3 计算结果缓存（动态数据）

**使用场景**：
- 缓存计算结果（避免重复计算）
- 数据变化频率高（每次计算都可能产生新结果）
- 需要短TTL（避免返回过期结果）

**实现方案**：使用 `cachetools.TTLCache`

**代码示例**：
```python
from cachetools import TTLCache, cached
from cachetools.keys import hashkey
import threading

# 创建TTL缓存（10分钟过期）
_calc_cache = TTLCache(maxsize=10000, ttl=600)
_calc_cache_lock = threading.RLock()


@cached(cache=_calc_cache, lock=_calc_cache_lock,
        key=lambda device_id, metric_key, ts: hashkey(device_id, metric_key, ts))
def get_calculated_value_cached(device_id: int, metric_key: str, ts: str) -> float:
    """
    获取计算结果（带缓存）
    
    缓存策略：
    - 最大缓存10000个结果
    - TTL=10分钟（结果更新后10分钟内生效）
    - 线程安全
    """
    # 调用实际的计算逻辑
    value = calculate_metric(device_id, metric_key, ts)
    return value
```

**配置参数**：
- `maxsize=10000`：最多缓存10000个计算结果
- `ttl=600`：缓存10分钟后自动过期
- `lock=threading.RLock()`：线程安全

**缓存失效**：
- 自动失效：10分钟后自动过期
- 手动失效：调用 `_calc_cache.clear()`

## 4. Celery消息代理方案

### 4.1 方案选择

**推荐方案**：使用数据库作为Celery消息代理

**理由**：
- 无需额外依赖（数据库已有）
- 适合单机部署
- 任务量不大，性能足够
- 简化部署和维护

### 4.2 配置示例

**文件**：`app/core/config.py`

```python
class Settings(BaseSettings):
    # Celery配置（使用数据库作为broker）
    @property
    def celery_broker_url(self) -> str:
        """动态生成Celery broker URL"""
        return f"db+postgresql://{self.DB_USER}:{self.DB_PASSWORD}@{self.DB_HOST}:{self.DB_PORT}/{self.DB_NAME}"
    
    @property
    def celery_result_backend(self) -> str:
        """动态生成Celery result backend URL"""
        return f"db+postgresql://{self.DB_USER}:{self.DB_PASSWORD}@{self.DB_HOST}:{self.DB_PORT}/{self.DB_NAME}"
```

**文件**：`app/tasks/celery_app.py`

```python
from celery import Celery
from app.core.config import settings

celery_app = Celery(
    'pump_station_tasks',
    broker=settings.celery_broker_url,  # 数据库URL
    backend=settings.celery_result_backend  # 数据库URL
)
```

### 4.3 数据库表

Celery会自动创建以下表：
- `celery_taskmeta`：存储任务结果
- `celery_tasksetmeta`：存储任务集结果

**注意**：
- 定期清理已完成的任务记录（避免表过大）
- 为这些表添加索引（提高查询性能）

## 5. 性能评估

### 5.1 缓存命中率预估

| 缓存类型 | 预估命中率 | 理由 |
|---------|-----------|------|
| 方法注册信息 | >95% | 数据几乎不变化 |
| 计算参数 | >80% | 参数变化频率低 |
| 计算结果 | >60% | 重复计算较多 |

### 5.2 性能对比

| 指标 | Redis | 内存缓存 | 对比 |
|------|-------|---------|------|
| 读取延迟 | ~1ms | ~0.01ms | 内存缓存快100倍 |
| 写入延迟 | ~1ms | ~0.01ms | 内存缓存快100倍 |
| 吞吐量 | ~10万QPS | ~100万QPS | 内存缓存高10倍 |
| 内存占用 | 外部服务 | 进程内存 | 内存缓存占用进程内存 |
| 持久化 | 支持 | 不支持 | Redis可持久化 |
| 分布式 | 支持 | 不支持 | Redis支持分布式 |

**结论**：
- 单机部署场景，内存缓存性能远超Redis
- 不需要持久化和分布式，内存缓存完全满足需求

## 7. 风险评估

### 7.1 技术风险

| 风险 | 严重程度 | 缓解措施 |
|------|---------|---------|
| 内存占用过高 | 🟡 中等 | 限制缓存大小（maxsize参数） |
| 缓存数据不一致 | 🟡 中等 | 设置合理的TTL，定期清理缓存 |
| 进程重启缓存丢失 | 🟢 低 | 可接受（缓存会自动重建） |

### 7.2 业务风险

| 风险 | 严重程度 | 缓解措施 |
|------|---------|---------|
| 使用过期参数 | 🟡 中等 | 设置5分钟TTL，参数更新后5分钟内生效 |
| 返回过期结果 | 🟢 低 | 设置10分钟TTL，结果更新后10分钟内生效 |

## 8. 总结

### 8.1 方案优势

1. ✅ **无外部依赖**：不需要Redis、Memcached等服务
2. ✅ **性能优秀**：内存访问延迟极低（~0.01ms）
3. ✅ **线程安全**：支持多线程并发访问
4. ✅ **自动过期**：TTL机制自动清理过期数据
5. ✅ **易于维护**：代码简单，配置灵活
6. ✅ **成本低**：无需额外的服务器和维护成本

### 8.2 适用场景

- ✅ 单机部署
- ✅ 任务量适中（<10万QPS）
- ✅ 环境限制（无法使用Redis）
- ✅ 不需要持久化
- ✅ 不需要分布式缓存

### 8.3 不适用场景

- ❌ 分布式部署（多个进程需要共享缓存）
- ❌ 高并发场景（>100万QPS）
- ❌ 需要持久化（进程重启后缓存保留）
- ❌ 需要跨语言访问（如Python和Java共享缓存）
