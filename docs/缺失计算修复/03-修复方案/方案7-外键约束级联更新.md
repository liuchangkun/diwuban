# 方案7：外键约束级联更新修复

## 📋 问题分析

### 问题描述

**具体表现**：
- 所有外键约束的 UPDATE 规则都是 `NO ACTION`
- 如果维度表ID变化（如重新导入数据），依赖表的ID不会自动更新
- 会导致外键约束违反和数据不一致

**根本原因**：
- 创建外键约束时未指定 `ON UPDATE CASCADE`
- 默认使用 `NO ACTION` 规则

**影响范围**：
- 23个表有外键约束但缺少级联更新
- 7个核心业务表缺少外键约束
- 如果重新导入维度表数据，会导致严重问题

**严重程度**：🟡 **严重**（重要但不紧急）

---

## 🎯 修复目标

1. **为所有现有外键添加级联更新规则**：`ON UPDATE CASCADE`
2. **为缺少外键约束的核心业务表添加约束**
3. **确保数据一致性**：维度表ID变化时自动更新依赖表
4. **提供回滚方案**：如果出现问题可以快速回滚

---

## 🔧 修复方案

### 方案选择

**推荐方案**：添加级联更新规则（`ON UPDATE CASCADE`）

**理由**：
- 自动处理ID变化，无需业务代码修改
- 数据一致性有保障
- PostgreSQL原生支持，性能可靠

**备选方案**：使用业务代码标识符（不推荐，工作量太大）

## 🚨 风险评估

### 风险1：级联更新性能开销

**风险描述**：如果维度表ID变化，会触发大量依赖表的更新，可能导致性能问题

**缓解措施**：
- 在维护窗口执行ID变化操作
- 使用事务确保原子性
- 监控执行时间，如果超过阈值则回滚

### 风险2：外键约束违反

**风险描述**：如果依赖表中存在孤立数据（引用不存在的ID），添加外键约束会失败

**缓解措施**：
- 在添加约束前清理孤立数据
- 使用 `NOT VALID` 选项先添加约束，再验证数据

```sql
-- 先添加约束（不验证现有数据）
ALTER TABLE calculation_parameters
ADD CONSTRAINT calculation_parameters_device_id_fkey
    FOREIGN KEY (device_id) REFERENCES dim_devices(id)
    ON UPDATE CASCADE ON DELETE CASCADE
    NOT VALID;

-- 再验证约束
ALTER TABLE calculation_parameters
VALIDATE CONSTRAINT calculation_parameters_device_id_fkey;
```

### 风险3：死锁

**风险描述**：级联更新可能导致死锁

**缓解措施**：
- 在低峰期执行
- 使用较短的锁超时时间
- 监控死锁日志
