# 日志格式对比示例

## 📋 真实日志对比

### 场景 1：正常业务日志

#### 当前格式（pipe）

```
2025-11-25 09:36:48.672158+08|12796|MainProcess|31192|MainThread|pipeline.py|pipeline|execute|75|INFO|[Pipeline-Stage1-开始] DataLoader|{"任务ID": "test-log-1764034608", "设备ID": 1, "指标键": "pump_speed", "时间范围": "2024-11-20 11:00:00 ~ 2024-11-20 12:00:00"}
```

**问题**：
- 前缀占用 **88 字符**
- `MainProcess` 和 `MainThread` 重复出现，无实际价值
- 消息被挤压到右侧，不易阅读

---

#### 简洁模式（compact）

```
2025-11-25 09:36:48.672+08|INFO|pipeline.execute:75|[Pipeline-Stage1-开始] DataLoader|{"任务ID": "test-log-1764034608", "设备ID": 1, "指标键": "pump_speed", "时间范围": "2024-11-20 11:00:00 ~ 2024-11-20 12:00:00"}
```

**改进**：
- 前缀缩短到 **44 字符**（减少 50%）
- 移除冗余字段，保留核心信息
- 消息更突出，易于快速浏览

---

#### 详细模式（detailed）

```
2025-11-25 09:36:48.672158+08|INFO|pipeline.execute:75|T-31192|[Pipeline-Stage1-开始] DataLoader|{"任务ID": "test-log-1764034608", "设备ID": 1, "指标键": "pump_speed", "时间范围": "2024-11-20 11:00:00 ~ 2024-11-20 12:00:00"}
```

**改进**：
- 前缀缩短到 **54 字符**（减少 38%）
- 保留线程信息（紧凑格式 `T-31192`）
- 保留完整微秒精度

---

#### 调试模式（debug）

```
2025-11-25 09:36:48.672158+08|INFO|P-12796|T-31192|pipeline.execute:75|[Pipeline-Stage1-开始] DataLoader|{"任务ID": "test-log-1764034608", "设备ID": 1, "指标键": "pump_speed", "时间范围": "2024-11-20 11:00:00 ~ 2024-11-20 12:00:00"}
```

**改进**：
- 前缀缩短到 **64 字符**（减少 27%）
- 保留所有调试信息（进程ID、线程ID）
- 使用紧凑前缀（`P-`/`T-`）

---

### 场景 2：参数加载日志

#### 当前格式（pipe）

```
2025-11-25 09:36:48.672059+08|12796|MainProcess|31192|MainThread|parameter_manager.py|parameter_manager|_load_params_from_db_with_sources|213|INFO|[参数管理] 参数合并过程|{"指标键": "pump_speed", "泵站ID": 1, "设备ID": 1, "全局参数": {"calibration_a": 30.0, "calibration_b": 0.0, "f_ref": 50.0, "n_ref": 1500.0, "pole_pairs": 2.0, "slip": 0.02}, "泵站参数覆盖": {}, "设备参数覆盖": {}, "最终参数": {"calibration_a": 30.0, "calibration_b": 0.0, "f_ref": 50.0, "n_ref": 1500.0, "pole_pairs": 2.0, "slip": 0.02}, "参数总数": 6}
```

**问题**：
- 前缀占用 **126 字符**（函数名过长）
- 一行超过 **500 字符**，难以阅读
- 核心信息（参数内容）被挤到最右侧

---

#### 简洁模式（compact）

```
2025-11-25 09:36:48.672+08|INFO|parameter_manager._load_params:213|[参数管理] 参数合并过程|{"指标键": "pump_speed", "泵站ID": 1, "设备ID": 1, "全局参数": {"calibration_a": 30.0, "calibration_b": 0.0, "f_ref": 50.0, "n_ref": 1500.0, "pole_pairs": 2.0, "slip": 0.02}, "泵站参数覆盖": {}, "设备参数覆盖": {}, "最终参数": {"calibration_a": 30.0, "calibration_b": 0.0, "f_ref": 50.0, "n_ref": 1500.0, "pole_pairs": 2.0, "slip": 0.02}, "参数总数": 6}
```

**改进**：
- 前缀缩短到 **68 字符**（减少 46%）
- 函数名简化（`_load_params` 代替完整名称）
- 整体长度减少，更易阅读

## 🎯 推荐配置

### 生产环境

```yaml
# configs/logging.yaml
logging:
  format: "compact"  # 简洁模式
  level: "INFO"
```

**理由**：
- 日志量大，需要节省存储空间
- 运维人员需要快速浏览日志
- 大部分情况下不需要进程/线程信息

---

### 开发环境

```yaml
# configs/logging.yaml
logging:
  format: "detailed"  # 详细模式
  level: "DEBUG"
```

**理由**：
- 需要更多调试信息
- 保留线程信息，便于多线程调试
- 保留完整时间精度

---

### 故障排查

```yaml
# configs/logging.yaml
logging:
  format: "debug"  # 调试模式
  level: "DEBUG"
```

**理由**：
- 需要所有可用信息
- 进程/线程信息对排查并发问题很重要
- 完整的代码位置信息

---

## ✅ 总结

**简洁模式**是最佳选择，因为：

1. ✅ **前缀缩短 46%**，显著提升可读性
2. ✅ **保留核心信息**，不影响日常调试
3. ✅ **适合生产环境**，节省存储和带宽
4. ✅ **易于快速浏览**，提高运维效率

**建议**：
- 默认使用**简洁模式**
- 通过环境变量或配置文件切换到其他模式
- 保留当前 `pipe` 格式作为向后兼容选项
