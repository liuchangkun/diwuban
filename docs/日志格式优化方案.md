# 日志格式优化方案

## 📋 当前日志格式分析

### 1. 当前格式示例

```
2025-11-25 09:36:48.672158+08|12796|MainProcess|31192|MainThread|pipeline.py|pipeline|execute|75|INFO|[Pipeline-Stage1-开始] DataLoader|{"任务ID": "test-log-1764034608", "设备ID": 1, "指标键": "pump_speed"}
```

### 2. 字段组成详解

当前日志格式采用**管道符（`|`）分隔**的固定字段，共 **12 个字段**：

| 序号 | 字段名 | 示例值 | 说明 | 重要性 | 冗余度 |
|------|--------|--------|------|--------|--------|
| 1 | `timestamp` | `2025-11-25 09:36:48.672158+08` | 时间戳（含微秒+时区） | ⭐⭐⭐⭐⭐ | 低 |
| 2 | `pid` | `12796` | 进程ID | ⭐⭐ | 中 |
| 3 | `processName` | `MainProcess` | 进程名称 | ⭐ | **高** |
| 4 | `threadId` | `31192` | 线程ID | ⭐⭐ | 中 |
| 5 | `threadName` | `MainThread` | 线程名称 | ⭐ | **高** |
| 6 | `filename` | `pipeline.py` | 文件名 | ⭐⭐⭐⭐ | 低 |
| 7 | `module` | `pipeline` | 模块名 | ⭐⭐⭐ | 中 |
| 8 | `funcName` | `execute` | 函数名 | ⭐⭐⭐⭐ | 低 |
| 9 | `lineno` | `75` | 行号 | ⭐⭐⭐ | 低 |
| 10 | `level` | `INFO` | 日志级别 | ⭐⭐⭐⭐⭐ | 低 |
| 11 | `message` | `[Pipeline-Stage1-开始] DataLoader` | 日志消息 | ⭐⭐⭐⭐⭐ | 低 |
| 12 | `extra_json` | `{"任务ID": "...", "设备ID": 1}` | 结构化数据（JSON） | ⭐⭐⭐⭐⭐ | 低 |

### 3. 问题诊断

#### 🔴 **高冗余字段**（单进程应用中）

1. **`processName`**：始终为 `MainProcess`，占用 11 字符
2. **`threadName`**：大部分为 `MainThread`，占用 10 字符
3. **`module`**：与 `filename` 高度重复（`pipeline.py` vs `pipeline`）

#### 🟡 **中等价值字段**（调试时有用，日常查看价值低）

1. **`pid`**：进程ID，多进程部署时有用，单进程时冗余
2. **`threadId`**：线程ID，多线程调试时有用
3. **`lineno`**：行号，精确定位代码位置，但增加前缀长度

#### 🟢 **核心字段**（必须保留）

1. **`timestamp`**：时间戳，日志分析的基础
2. **`level`**：日志级别，过滤和告警的依据
3. **`filename`** + **`funcName`**：代码位置，快速定位问题
4. **`message`**：日志消息，核心信息
5. **`extra_json`**：结构化数据，业务上下文

### 4. 当前格式的优缺点

#### ✅ **优点**

1. **信息完整**：包含所有可能需要的调试信息
2. **结构化**：管道符分隔，易于解析和分析
3. **可配置**：通过 `configs/logging.yaml` 的 `fields.include` 控制字段
4. **中文化**：`extra_json` 支持中文键名，提高可读性

#### ❌ **缺点**

1. **前缀过长**：固定前缀占用 80-100 字符，挤压消息空间
2. **冗余信息多**：单进程应用中，`MainProcess`/`MainThread` 重复出现
3. **可读性差**：技术细节过多，不利于快速浏览
4. **缺少分层**：所有环境（开发/生产）使用相同格式，无法按需调整

## 🎯 优化方案

### 方案 A：**简洁模式**（推荐用于生产环境）

**目标**：保留核心信息，移除冗余字段，提高可读性

#### 格式设计

```
时间戳 | 级别 | 位置 | 消息 | 数据
```

#### 示例输出

```
2025-11-25 09:36:48.672+08|INFO|pipeline.execute:75|[Pipeline-Stage1-开始] DataLoader|{"任务ID": "test-log-1764034608", "设备ID": 1}
```

#### 字段说明

| 字段 | 格式 | 说明 |
|------|------|------|
| 时间戳 | `YYYY-MM-DD HH:MM:SS.mmm+TZ` | 精确到毫秒（简化微秒） |
| 级别 | `INFO/ERROR/DEBUG` | 日志级别 |
| 位置 | `module.function:line` | 代码位置（紧凑格式） |
| 消息 | 原始消息 | 日志消息 |
| 数据 | JSON | 结构化数据 |

#### 优点

- ✅ **前缀缩短 50%**：从 ~90 字符减少到 ~45 字符
- ✅ **可读性提升**：核心信息一目了然
- ✅ **保留关键调试信息**：时间、级别、位置、消息、数据

#### 配置修改

```yaml
# configs/logging.yaml
logging:
  format: "compact"  # 新增格式选项
  fields:
    include:
      - timestamp_short  # 简化时间戳（毫秒）
      - level
      - location  # 组合字段：module.function:line
      - message
      - extra_json
```

### 方案 B：**详细模式**（推荐用于开发环境）

**目标**：保留更多调试信息，但优化字段顺序和格式

#### 格式设计

```
时间戳 | 级别 | 位置 | 线程 | 消息 | 数据
```

#### 示例输出

```
2025-11-25 09:36:48.672158+08|INFO|pipeline.execute:75|T-31192|[Pipeline-Stage1-开始] DataLoader|{"任务ID": "test-log-1764034608"}
```

#### 字段说明

| 字段 | 格式 | 说明 |
|------|------|------|
| 时间戳 | `YYYY-MM-DD HH:MM:SS.ffffff+TZ` | 完整微秒精度 |
| 级别 | `INFO/ERROR/DEBUG` | 日志级别 |
| 位置 | `module.function:line` | 代码位置 |
| 线程 | `T-{threadId}` | 线程ID（紧凑格式） |
| 消息 | 原始消息 | 日志消息 |
| 数据 | JSON | 结构化数据 |

#### 优点

- ✅ **保留线程信息**：多线程调试时有用
- ✅ **前缀缩短 40%**：从 ~90 字符减少到 ~55 字符
- ✅ **移除冗余**：去掉 `MainProcess`/`MainThread`

---

### 方案 C：**调试模式**（推荐用于故障排查）

**目标**：保留所有信息，但优化格式和顺序

#### 格式设计

```
时间戳 | 级别 | 进程 | 线程 | 位置 | 消息 | 数据
```

#### 示例输出

```
2025-11-25 09:36:48.672158+08|INFO|P-12796|T-31192|pipeline.execute:75|[Pipeline-Stage1-开始] DataLoader|{"任务ID": "test-log-1764034608"}
```

#### 字段说明

| 字段 | 格式 | 说明 |
|------|------|------|
| 时间戳 | `YYYY-MM-DD HH:MM:SS.ffffff+TZ` | 完整微秒精度 |
| 级别 | `INFO/ERROR/DEBUG` | 日志级别 |
| 进程 | `P-{pid}` | 进程ID（紧凑格式） |
| 线程 | `T-{threadId}` | 线程ID（紧凑格式） |
| 位置 | `module.function:line` | 代码位置 |
| 消息 | 原始消息 | 日志消息 |
| 数据 | JSON | 结构化数据 |

#### 优点

- ✅ **信息完整**：保留所有调试信息
- ✅ **格式优化**：使用紧凑前缀（`P-`/`T-`）
- ✅ **前缀缩短 30%**：从 ~90 字符减少到 ~65 字符

## 🛠️ 实施建议

### 1. 配置文件修改

在 `configs/logging.yaml` 中添加格式选项：

```yaml
logging:
  format: "compact"  # 可选：compact|detailed|debug|pipe（默认）
```

### 2. 代码修改

修改 `app/core/logging/setup.py` 中的 `PipeFormatter` 类，支持多种格式。

### 3. 环境变量控制

允许通过环境变量覆盖配置：

```bash
# 生产环境
export LOG_FORMAT=compact

# 开发环境
export LOG_FORMAT=detailed

# 调试环境
export LOG_FORMAT=debug
```

### 4. 向后兼容

保留当前的 `pipe` 格式作为默认值，确保现有系统不受影响。
