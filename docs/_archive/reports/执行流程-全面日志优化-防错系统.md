## 🎯 核心目标

**建立完善的不会出错的任务和检查和验证流程**

因为修改的文件很多（142个），必须确保：
- ✅ 每个文件修改前都有完整的验证
- ✅ 每个文件修改后都有完整的检查
- ✅ 每个阶段完成后都有完整的测试
- ✅ 任何错误都能立即发现和回滚
- ✅ 所有修改都有详细的记录

## 🔒 防错机制（5层防护）

### 第1层：修改前验证

**目的**：确保修改的文件和位置正确

**检查项**：
1. ✅ 文件存在性验证
2. ✅ 文件内容验证（使用 `view` 工具）
3. ✅ 现有日志搜索（使用 `search_query_regex`）
4. ✅ 函数签名验证（确认函数存在）
5. ✅ 依赖关系验证（确认导入正确）

**工具**：
- `view` - 查看文件内容
- `search_query_regex` - 搜索现有日志
- `codebase-retrieval` - 验证函数签名
- `diagnostics` - 检查语法错误

**示例**：
```markdown
### 修改前验证：app/services/rules/auto_baseline_b.py

- [ ] 使用 view 工具查看整个文件
- [ ] 搜索现有日志：search_query_regex "_act\.(info|warning|error|debug)"
- [ ] 确认函数签名：run_auto_baseline_b(settings, lookback_days, station_id, device_id, method, version)
- [ ] 确认导入：from app.core.logging.setup import get_logger
- [ ] 检查语法：diagnostics app/services/rules/auto_baseline_b.py
```

---

### 第2层：修改中控制

**目的**：确保修改操作正确执行

**检查项**：
1. ✅ 使用 `str-replace-editor` 工具（不使用其他工具）
2. ✅ 每次修改不超过150行
3. ✅ 精确匹配 `old_str`（包括空格、缩进）
4. ✅ 指定行号范围（`old_str_start_line_number`、`old_str_end_line_number`）
5. ✅ 验证修改结果（工具返回成功消息）

**工具**：
- `str-replace-editor` - 唯一的文件修改工具

**禁止**：
- ❌ 不使用 `save-file` 覆盖现有文件
- ❌ 不使用 `launch-process` 执行 `sed`、`awk` 等命令
- ❌ 不使用其他任何文件修改工具

**示例**：
```markdown
### 修改操作：添加日志导入

- [ ] 使用 str-replace-editor 工具
- [ ] 指定 old_str（精确匹配，包括缩进）
- [ ] 指定 old_str_start_line_number 和 old_str_end_line_number
- [ ] 指定 new_str（包含新的导入语句）
- [ ] 验证工具返回 "Replacement successful"
```

---

### 第3层：修改后检查

**目的**：确保修改结果正确

**检查项**：
1. ✅ 使用 `view` 工具查看修改后的代码
2. ✅ 使用 `diagnostics` 工具检查语法错误
3. ✅ 验证日志格式（使用 `search_query_regex`）
4. ✅ 验证没有重复的日志
5. ✅ 验证没有未使用的导入

**工具**：
- `view` - 查看修改后的文件
- `diagnostics` - 检查语法错误
- `search_query_regex` - 验证日志格式

**示例**：
```markdown
### 修改后检查：app/services/rules/auto_baseline_b.py

- [ ] 使用 view 工具查看修改后的代码
- [ ] 使用 diagnostics 工具检查语法错误
- [ ] 搜索所有日志：search_query_regex "\[.*?\]"
- [ ] 确认没有重复的日志
- [ ] 确认没有未使用的导入
```

---

### 第4层：阶段性测试

**目的**：确保修改的文件能正常运行

**检查项**：
1. ✅ 运行相关CLI命令
2. ✅ 检查日志输出
3. ✅ 验证数据库操作
4. ✅ 验证计算结果
5. ✅ 创建阶段测试报告

**工具**：
- `launch-process` - 运行CLI命令
- `read-terminal` - 读取命令输出
- `query_PostgreSQL` - 验证数据库

**示例**：
```markdown
### 阶段测试：规则生成函数（6个文件）

- [ ] 运行 rules:refresh-all 命令
- [ ] 检查 logs/app.log 中的日志输出
- [ ] 验证规则表是否有数据
- [ ] 验证日志格式是否统一
- [ ] 创建阶段测试报告
```

---

**目的**：确保所有修改都正确且系统正常运行

**检查项**：

3. ✅ 验证所有数据库表

**工具**：

- `query_PostgreSQL` - 验证数据库表

**示例**：

## 🔄 执行流程（标准化）

### 单个文件的执行流程

**步骤1：修改前验证**（5分钟）
```markdown
1. [ ] 使用 view 工具查看整个文件
2. [ ] 搜索现有日志
3. [ ] 确认函数签名
4. [ ] 确认导入
5. [ ] 检查语法
```

**步骤2：修改操作**（10分钟）
```markdown
1. [ ] 添加日志导入（如果没有）
2. [ ] 添加/完善日志（按照日志策略）
3. [ ] 替换低质量日志（如 log_db_function）
4. [ ] 删除冗余代码
5. [ ] 验证修改结果
```

**步骤3：修改后检查**（5分钟）
```markdown
1. [ ] 使用 view 工具查看修改后的代码
2. [ ] 使用 diagnostics 工具检查语法错误
3. [ ] 验证日志格式
4. [ ] 验证没有重复的日志
5. [ ] 验证没有未使用的导入
```

**步骤4：更新任务状态**（1分钟）
```markdown
1. [ ] 使用 update_tasks 标记任务为 COMPLETE
2. [ ] 记录修改摘要
3. [ ] 继续下一个文件
```

**单个文件总耗时**：约21分钟

## 🚨 错误处理流程

### 发现错误时的处理步骤

**步骤1：立即停止**
```markdown
1. [ ] 停止当前操作
2. [ ] 标记当前任务为 CANCELLED
3. [ ] 记录错误详情
```

**步骤2：分析错误**
```markdown
1. [ ] 确定错误类型（语法错误、逻辑错误、运行时错误）
2. [ ] 确定错误原因
3. [ ] 确定影响范围
```

**步骤3：回滚修改**（如果需要）
```markdown
1. [ ] 使用 git 查看修改历史
2. [ ] 使用 str-replace-editor 回滚错误的修改
3. [ ] 验证回滚结果
```

**步骤4：修复错误**
```markdown
1. [ ] 制定修复方案
2. [ ] 执行修复操作
3. [ ] 验证修复结果
```

**步骤5：继续执行**
```markdown
1. [ ] 更新任务状态
2. [ ] 继续下一个文件
```
