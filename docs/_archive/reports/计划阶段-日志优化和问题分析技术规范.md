## 🎯 核心问题分析

### 问题1：规则表为空的根本原因

**现象**：
- metric_rule_auto_baseline: 0行
- metric_rule_auto_baseline_shadow: 0行
- metric_quality_rules: 0行
- metric_quality_rules_shadow: 0行
- device_running_thresholds: 8行
- device_running_thresholds_shadow: 0行

**根本原因**：
1. **时间窗口不匹配**（主要原因）：
   - 规则生成函数使用 `lookback_days=30`，查询窗口：2025-09-20 到 2025-10-20
   - 实际数据时间范围：2025-05-31 18:00:00 到 19:59:59（**3个月前**）
   - **窗口完全不重叠** → 查询返回0行

2. **数据时间跨度太短**（次要原因）：
   - 当前数据跨度：**2小时**
   - 规则生成需要：**至少30天**的历史数据
   - 即使修正时间窗口，2小时数据也不足以计算稳健的基线

3. **硬编码的最小数据量要求**：
   - `auto_baseline_b.py` 第154行：`if df.index.size < 120`（需要120个数据点 = 2小时）
   - `running_thresholds_b.py` 第18行：`if x.size < 200`（需要200个PF值 = 3.33小时）

4. **数据库存储过程的时间窗口硬编码**：
   - `sp_refresh_metric_rule_auto_baseline` 使用 `now()` 作为结束时间
   - 如果数据是历史数据，窗口完全不匹配

**解决方案**：
- **方案A**：修改规则生成函数，使用实际数据窗口
- **方案B**：降低最小数据量要求（120 → 30, 200 → 50）
- **方案C**：添加详细的日志输出，说明跳过原因

### 问题3：备份恢复失败

**现象**：
- 4个表的备份SQL有语法错误
- 时间戳字段解析问题：`syntax error at or near "15"`

**根本原因**：
- 备份SQL生成时，时间戳值缺少引号
- 示例错误：`INSERT INTO ... VALUES (..., 2025-10-20 14:22:49.056537+08, ...)`
- 正确格式：`INSERT INTO ... VALUES (..., '2025-10-20 14:22:49.056537+08', ...)`

**解决方案**：
- 修改 `BackupManager._generate_sql_backup()` 方法
- 为所有值添加适当的引号和类型转换

### 任务组3：备份恢复失败（方案A）

#### 更改3.1：修复备份SQL生成逻辑

**文件**：`app/services/ingest/prepare_dim/backup.py`

**理由**：
- 修复时间戳字段的SQL语法错误
- 确保所有值都有适当的引号和类型转换

**具体更改**：

**位置**：`_generate_sql_backup()` 方法（第295-395行）

**原代码问题**：
- 时间戳值缺少引号
- 示例：`2025-10-20 14:22:49.056537+08`
- 正确格式：`'2025-10-20 14:22:49.056537+08'`

**新代码**：
```python
def _generate_sql_backup(self, cur, table_name: str) -> str:
    """生成SQL备份脚本，修复时间戳引号问题"""
    
    # ... 前面的代码保持不变 ...
    
    # 生成INSERT语句
    for row in rows:
        values = []
        for i, (col_name, col_type) in enumerate(columns):
            value = row[i]
            if value is None:
                values.append('NULL')
            elif col_type in ('timestamp with time zone', 'timestamp without time zone', 'timestamptz'):
                # 时间戳类型：添加引号
                values.append(f"'{value}'")
            elif col_type in ('text', 'character varying', 'varchar', 'char'):
                # 字符串类型：添加引号并转义单引号
                escaped_value = str(value).replace("'", "''")
                values.append(f"'{escaped_value}'")
            elif col_type in ('integer', 'bigint', 'smallint', 'numeric', 'real', 'double precision'):
                # 数值类型：不添加引号
                values.append(str(value))
            elif col_type == 'boolean':
                # 布尔类型：转换为 true/false
                values.append('true' if value else 'false')
            else:
                # 其他类型：添加引号
                values.append(f"'{value}'")
        
        # 生成INSERT语句
        sql_lines.append(f"INSERT INTO {table_name} ({', '.join(column_names)}) VALUES ({', '.join(values)})")
        sql_lines.append("ON CONFLICT (...) DO UPDATE SET ...;")
    
    return "\n".join(sql_lines)
```

**涉及的函数/类**：
- `BackupManager._generate_sql_backup()` 方法

**依赖关系**：
- 依赖数据库连接：`psycopg`

## 🔍 潜在问题和缺陷清单

### 问题4：数据库存储过程的返回值不一致

**位置**：`app/services/ingest/prepare_dim/__init__.py` 第1260-1262行

**问题**：
```python
total_rules = sum(v["count"] if isinstance(v, dict) else v for v in rule_result.values())
```
- 代码假设返回值可能是 `{"count": N}` 或直接是数字
- 但实际上 `run_auto_baseline_b` 返回 `{"inserted": 0}`（不是 `count`）

**解决方案**：
- 统一所有规则生成函数的返回值格式
- 使用 `inserted` 而不是 `count`

---

### 问题5：规则生成函数的事务处理不一致

**位置**：`prepare_dim/__init__.py` 第1252-1259行

**问题**：
- 清空操作在一个事务中
- 生成操作在独立事务中
- 如果生成失败，表已经被清空，无法回滚

**解决方案**：
- 使用同一个事务，或者先备份再清空

---

### 问题6：日志格式不统一

**位置**：多个文件

**问题**：
- 有些日志使用 `[操作标签] 消息`
- 有些日志直接输出消息，没有标签
- 有些日志使用 `extra_json`，有些不使用

**解决方案**：
- 制定统一的日志格式规范
- 所有关键操作都必须有标签
- 所有结构化数据都使用 `extra_json`

---

### 问题7：日志级别使用不当

**位置**：多个文件

**问题**：
- 有些 ERROR 日志实际上是 WARNING
- 有些 INFO 日志实际上应该是 DEBUG

**解决方案**：
- 重新评估所有日志的级别
- ERROR：系统错误、数据损坏
- WARNING：预期外的情况、降级处理
- INFO：关键业务操作
- DEBUG：详细的调试信息

---

### 问题8：日志缺少上下文信息

**位置**：多个文件

**问题**：
- 有些日志只有消息，没有设备ID、站点ID等上下文
- 难以追踪特定设备的处理流程

**解决方案**：
- 所有日志都应包含：站点ID、设备ID、指标ID（如果适用）
- 使用 `extra_json` 统一传递上下文信息

---

### 问题9：日志时间戳时区不一致

**位置**：`configs/logging.yaml`

**问题**：
- 日志时间戳使用 `+08` 时区
- 数据库时间戳使用 UTC
- 可能导致时间对比困难

**解决方案**：
- 统一使用 UTC 时区
- 或者在日志中同时显示 UTC 和本地时间
