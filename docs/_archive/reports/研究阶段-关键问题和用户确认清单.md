### 问题1：fact_measurements 表的清空策略 ⚠️ **极高优先级**

**当前实现**:
```python
def _clear_non_backup_tables(cur) -> int:
    # 第1层：叶子节点（无外键依赖）
    # fact_measurements: 所有历史数据
    cur.execute("DELETE FROM fact_measurements")
    deleted = cur.rowcount
    total_deleted += deleted
    _act.info(f"[清空表] fact_measurements: {deleted} 行")
```

**问题描述**:
- 当前 `_clear_non_backup_tables()` 函数会清空 `fact_measurements` 表
- `fact_measurements` 是核心数据表，包含所有历史测量数据
- 规则表生成（stage 2）依赖 `fact_measurements` 的历史数据（近30天）
- 如果清空 `fact_measurements`，规则表无法生成

**影响范围**:
- ❌ 清空后，所有历史数据丢失
- ❌ 规则表生成失败（无数据可用）
- ❌ 需要重新导入所有历史数据

**用户需求确认**:
1. ❓ 是否应该清空 `fact_measurements` 表？
2. ❓ 如果清空，如何确保规则表生成有足够的历史数据？
3. ❓ 是否应该添加配置选项控制是否清空？

**建议方案**:
- **方案A**: 不清空 `fact_measurements` 表（推荐）
  - 优点：保留历史数据，规则表可正常生成
  - 缺点：可能包含脏数据
- **方案B**: 添加配置选项控制是否清空
  - 优点：灵活性高
  - 缺点：增加复杂度
- **方案C**: 清空但要求用户先导入历史数据
  - 优点：数据干净
  - 缺点：流程复杂，容易出错

### 问题2：配置表的双重恢复逻辑 ⚠️ **高优先级**

**当前实现**:
```python
# Stage 1.4: 恢复10个配置表（从备份）
config_tables = [
    "calculation_method_registry",
    "calculation_parameters",
    "device_rated_params",
    "metric_calculation_order",
    ...
]
for table_name in config_tables:
    restore_result = backup_manager.restore_table(cur, table_name)

# Stage 1.5: 重建4个配置表（从SQL脚本或代码生成）
_rebuild_config_tables(settings, cur)
# 1. calculation_method_registry（init_methods.sql）
# 2. calculation_parameters（init_params.sql）
# 3. device_rated_params（20250829_seed_device_rated_params.sql）
# 4. metric_calculation_order（DependencyAnalyzer.save_to_database()）
```

**问题描述**:
- Stage 1.4 从备份恢复4个配置表
- Stage 1.5 又从SQL脚本重建这4个表
- 存在重复逻辑，可能导致数据覆盖

**影响范围**:
- ⚠️ 优化后的参数可能被覆盖
- ⚠️ 执行效率低（重复操作）
- ⚠️ 逻辑不清晰

**用户需求确认**:
1. ❓ 为什么要先从备份恢复，再从SQL脚本重建？
2. ❓ 是否应该只执行其中一种策略？
3. ❓ 如果需要保留优化后的参数，应该如何处理？

**建议方案**:
- **方案A**: 只从备份恢复（推荐）
  - 优点：保留优化后的参数
  - 缺点：如果备份不存在，无法恢复
- **方案B**: 只从SQL脚本重建
  - 优点：确保基础数据存在
  - 缺点：丢失优化后的参数
- **方案C**: 先尝试从备份恢复，失败则从SQL脚本重建
  - 优点：兼顾两者
  - 缺点：逻辑复杂
