# 业务逻辑分类与外键需求分析

## 📋 文档信息

**分析日期**：2025-10-27  
**分析目标**：区分"配置数据"和"历史数据"，确定哪些表需要跟随维度表ID变化  
**核心原则**：配置影响程序如何运行，历史记录程序运行的结果  
**文档版本**：v1.0

---

## 🎯 核心观点

### 配置数据 vs 历史数据

| 维度 | 配置数据 | 历史数据 |
|------|---------|---------|
| **定义** | 影响程序如何运行的参数和规则 | 记录程序运行结果的数据 |
| **用途** | 被程序读取用于决策和计算 | 用于查询、分析和报表 |
| **ID变化影响** | 配置失联导致功能失效 | 保留历史ID是合理的 |
| **是否需要外键** | ✅ 是（必须跟随ID变化） | ❌ 否（保持历史记录不变） |
| **示例** | 设备额定参数、运行阈值、质量规则 | 时序测量数据、运行日志、性能指标 |

### 关键判断标准

**如何判断一个表是"配置数据"？**

1. **程序读取测试**：程序启动或运行时是否读取该表？
2. **决策影响测试**：该表的数据是否影响程序的计算逻辑或判断逻辑？
3. **失联影响测试**：如果该表的数据无法关联到设备，程序是否会出错或功能失效？

**如果以上3个问题的答案都是"是"，则该表是配置数据，需要外键约束。**

## 🔍 详细业务逻辑分析

### 1. device_running_thresholds（P0 - 立即处理）

**表用途**：设备启停判定与相位窗口阈值表

**在系统中的作用**：
1. **运行状态判定**：程序读取该表的阈值（功率、电流、频率）判断设备是否运行
2. **相位窗口判定**：程序读取该表的时间参数（grace_hold_secs, min_run_secs等）判断启停窗口
3. **功率因数判定**：程序读取该表的功率因数阈值（pf_min, pf_max）判断设备运行质量

**代码使用证据**：

<augment_code_snippet path="app/adapters/db/device_running_sql.py" mode="EXCERPT">
````python
def list_default_device_ids(cur) -> List[int]:
    """默认设备集合：全部泵类设备（排除 main_pipeline），且在阈值表存在配置。"""
    sql = """
        SELECT d.id
        FROM public.dim_devices d
        JOIN public.device_running_thresholds t ON t.device_id = d.id
        WHERE COALESCE(NULLIF(d.type,''),'') NOT IN ('main_pipeline','clear_water_pool','other')
          AND COALESCE(d.is_active, TRUE) = TRUE
        ORDER BY d.id
        """
````
</augment_code_snippet>

**如果ID不同步会导致的问题**：
1. ❌ **运行状态判定失效**：程序无法获取设备的阈值配置，导致无法判断设备是否运行
2. ❌ **启停窗口检测失效**：程序无法获取时间参数，导致无法检测启停窗口
3. ❌ **功率因数判定失效**：程序无法获取功率因数阈值，导致无法判断设备运行质量
4. ❌ **设备被排除在计算范围外**：`list_default_device_ids()` 函数依赖该表，ID失联后设备不会被包含在计算列表中

**优先级**：**P0 - 立即执行**

**建议措施**：立即添加外键约束

### 6. fact_measurements（历史数据 - 不需要外键）

**表用途**：事实表（秒级对齐）

**在系统中的作用**：
1. **历史数据查询**：用于查询设备的历史测量数据
2. **统计分析**：用于统计分析和报表生成

**为什么不需要外键约束**：
1. ✅ **历史记录应保持不变**：历史数据记录的是过去某个时间点的设备状态，即使设备ID变化，历史记录也应该保持不变
2. ✅ **TimescaleDB限制**：fact_measurements 是 TimescaleDB Hypertable，使用 device_id 作为空间分区列，无法添加外键约束
3. ✅ **不影响程序运行逻辑**：程序不依赖 fact_measurements 的数据来决定如何运行，只用于查询和分析

**正确的处理方式**：
- 保留历史ID，不跟随维度表ID变化
- 如果需要查询历史数据，使用设备名称（station_name, device_name）而不是ID
- 如果设备被删除，历史数据仍然保留（用于审计和分析）

#### 任务1：为 device_running_thresholds 添加外键约束（P0）

**SQL脚本**：
```sql
-- 执行前检查孤立记录
SELECT COUNT(*) FROM device_running_thresholds drt
LEFT JOIN dim_devices d ON d.id = drt.device_id
WHERE d.id IS NULL;

-- 添加外键约束
ALTER TABLE device_running_thresholds
ADD CONSTRAINT device_running_thresholds_device_id_fkey
FOREIGN KEY (device_id) REFERENCES dim_devices(id)
ON UPDATE CASCADE ON DELETE CASCADE;
```

**预期效果**：
- ✅ 运行阈值配置会自动跟随设备ID变化
- ✅ 删除设备时阈值配置会自动清理
- ✅ 防止阈值配置出现孤立记录

## 📊 总结

### 核心发现

1. **配置数据表**：14个，其中5个缺少外键约束
2. **历史数据表**：12个，其中8个已有外键（用于自动清理），4个无外键（保留历史记录）
3. **物化视图**：3个，不需要外键约束

### 优先级分布

| 优先级 | 表数量 | 说明 |
|--------|--------|------|
| P0（立即执行） | 1个 | device_running_thresholds |
| P1（1个月内） | 4个 | metric_quality_rules, metric_rule_auto_baseline, metric_anomaly_strategy, device_metric_candidates |
| P2（长期规划） | 0个 | - |

### 关键结论

1. ✅ **fact_measurements 不需要外键约束**：这是历史数据表，保留历史ID是合理的
2. ✅ **device_running_thresholds 必须添加外键约束**：这是配置表，影响运行状态判定
3. ✅ **质量规则相关表应添加外键约束**：这些是配置表，影响质量评价和异常检测
4. ✅ **物化视图不需要外键约束**：定期刷新时会自动使用最新的ID
