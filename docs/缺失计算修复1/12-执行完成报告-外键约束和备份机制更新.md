## 🔍 验证结果

### 外键约束验证

**查询SQL**：
```sql
SELECT 
    tc.table_name AS 源表名,
    kcu.column_name AS 源列名,
    ccu.table_name AS 目标表名,
    ccu.column_name AS 目标列名,
    rc.update_rule AS UPDATE规则,
    rc.delete_rule AS DELETE规则
FROM information_schema.table_constraints AS tc 
JOIN information_schema.key_column_usage AS kcu
    ON tc.constraint_name = kcu.constraint_name
JOIN information_schema.constraint_column_usage AS ccu
    ON ccu.constraint_name = tc.constraint_name
JOIN information_schema.referential_constraints AS rc
    ON rc.constraint_name = tc.constraint_name
WHERE tc.constraint_type = 'FOREIGN KEY'
    AND tc.table_name IN (
        'calculation_validation_config',
        'device_running_thresholds',
        'metric_anomaly_strategy',
        'metric_quality_rules',
        'metric_rule_auto_baseline',
        'metric_capability_policy'
    )
    AND tc.table_schema = 'public'
ORDER BY tc.table_name, kcu.column_name;
```

**预期结果**：
- calculation_validation_config: 3个外键（station_id, device_id, metric_key）
- device_running_thresholds: 1个外键（device_id）
- metric_anomaly_strategy: 3个外键（station_id, device_id, metric_id）
- metric_quality_rules: 3个外键（station_id, device_id, metric_id）
- metric_rule_auto_baseline: 3个外键（station_id, device_id, metric_id）
- metric_capability_policy: 1个外键（metric_key）

**所有外键的级联规则**：
- UPDATE规则：CASCADE
- DELETE规则：CASCADE

## ❓ 常见问题

### Q1：为什么要添加 optimization_history 到备份机制？

**A**：虽然 optimization_history 是历史记录表，但它包含RLS（递归最小二乘）增量优化的关键状态信息（协方差矩阵、RLS状态等）。这些信息对于参数优化的连续性至关重要，不能丢失。因此将其归类为"需要备份导入"的A类手动配置表。

### Q2：为什么 device_metric_candidates 和 dim_metric_metadata 需要备份？

**A**：
- `device_metric_candidates`：设备指标候选表，用于确定哪些指标需要计算，属于配置数据
- `dim_metric_metadata`：指标元数据表，包含指标的额外元数据信息，属于配置数据

这两个表都影响程序如何运行，因此需要备份。

### Q3：为什么要在清空 dim_devices 之前清空 metric_anomaly_strategy 和 optimization_history？

**A**：这两个表有外键依赖 `dim_devices`（ON DELETE CASCADE）。虽然外键约束会自动级联删除，但为了明确记录清空操作和行数，我们在清空 `dim_devices` 之前手动清空这两个表。
