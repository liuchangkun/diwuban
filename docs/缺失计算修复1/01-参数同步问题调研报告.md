# 参数同步问题调研报告

## 📋 执行摘要

### 任务背景
系统中存在数据一致性问题：当维度表 `dim_devices.id`（设备ID）或 `dim_stations.id`（泵站ID）发生变化时，依赖这些ID的指标计算参数和优化参数没有同步更新,导致以下问题：
1. 设备和泵站无法正常进行指标计算（因参数关联失效）
2. 计算所需的参数无法正确获取或匹配
3. 优化功能因缺少有效参数而无法正常运行

### 调研目标
1. 定位所有依赖 `dim_devices.id` 和 `dim_stations.id` 的参数表和配置表
2. 分析当前的参数关联机制和更新逻辑
3. 识别导致参数失联的具体场景
4. 评估现有的外键约束和级联更新机制

### 核心发现
1. ✅ **外键约束已全部配置级联更新**：28个表的外键约束已设置 `ON UPDATE CASCADE`
2. ✅ **参数加载机制完善**：5层参数优先级系统已实现
3. ⚠️ **维度表ID实际上很稳定**：使用UPSERT策略，ID不会轻易变化
4. ⚠️ **真实风险场景有限**：只有在特定操作下才会导致ID变化

## 二、参数关联机制分析

### 2.1 参数加载机制（5层优先级）

**代码位置**：`app/services/calculation/orchestrator.py` (lines 683-805)

**参数来源优先级**（从低到高）：
1. **全局计算参数**（calculation_parameters, device_id=NULL, station_id=NULL）
2. **全局默认额定参数**（global_default_rated_params）
3. **设备额定参数**（device_rated_params, device_id=X）
4. **泵站级计算参数**（calculation_parameters, station_id=X, device_id=NULL）
5. **设备级计算参数**（calculation_parameters, device_id=X）

**关键特性**：
- ✅ 支持参数覆盖（高优先级覆盖低优先级）
- ✅ 支持降级策略（设备无额定参数时使用全局默认值）
- ✅ 记录参数来源（用于调试）
- ✅ 支持多种参数类型（numeric、string）

### 2.2 参数表结构

#### calculation_parameters 表（22个字段）
```sql
CREATE TABLE calculation_parameters (
    id                   BIGSERIAL PRIMARY KEY,
    station_id           BIGINT REFERENCES dim_stations(id) ON UPDATE CASCADE ON DELETE CASCADE,
    device_id            BIGINT REFERENCES dim_devices(id) ON UPDATE CASCADE ON DELETE CASCADE,
    metric_key           TEXT NOT NULL REFERENCES dim_metric_config(metric_key) ON UPDATE CASCADE ON DELETE CASCADE,
    method_id            TEXT NOT NULL REFERENCES calculation_method_registry(method_id),
    param_name           TEXT NOT NULL,
    param_value          NUMERIC NOT NULL,
    param_value_text     TEXT,                    -- 支持字符串类型参数
    param_type           TEXT NOT NULL DEFAULT 'float',
    is_optimizable       BOOLEAN NOT NULL DEFAULT true,
    optimization_history JSONB,
    covariance_matrix    JSONB,                   -- RLS协方差矩阵
    rls_iterations       INTEGER DEFAULT 0,
    last_p_trace         NUMERIC,
    created_at           TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at           TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_by           TEXT NOT NULL DEFAULT 'system',
    confidence_score     NUMERIC DEFAULT 0.5,
    last_optimized_at    TIMESTAMPTZ,
    optimization_count   INTEGER DEFAULT 0,
    param_min            NUMERIC,
    param_max            NUMERIC,
    
    UNIQUE(station_id, device_id, method_id, param_name)
);
```

**关键约束**：
- 外键约束：device_id、station_id、metric_key 都设置了 `ON UPDATE CASCADE`
- 唯一约束：(station_id, device_id, method_id, param_name) 防止重复参数

## 三、ID变化场景分析

### 3.1 维度表ID的稳定性

**当前策略**：使用 UPSERT（INSERT ... ON CONFLICT ... DO UPDATE）

**代码位置**：`app/services/ingest/prepare_dim/__init__.py`

```python
# 当前代码已经使用 UPSERT
INSERT INTO dim_devices (station_id, name, type, pump_type)
VALUES (%s, %s, %s, %s)
ON CONFLICT (station_id, name) DO UPDATE
SET type = EXCLUDED.type, pump_type = EXCLUDED.pump_type
RETURNING id
```

**关键特性**：
- ✅ 使用 (station_id, name) 作为唯一约束
- ✅ 冲突时只更新属性，不改变ID
- ✅ ID由序列自动生成，只在新增时分配

### 3.2 可能导致ID变化的场景

#### 场景1：手动修改ID（极少发生）
```sql
UPDATE dim_devices SET id = 999 WHERE id = 121;
```
**影响**：
- ✅ 外键约束会自动级联更新所有依赖表
- ✅ calculation_parameters、device_rated_params、optimization_history 的 device_id 会自动更新为 999

#### 场景2：删除后重新插入（可能发生）
```sql
DELETE FROM dim_devices WHERE id = 121;  -- 级联删除所有依赖数据
INSERT INTO dim_devices (station_id, name, type) VALUES (12, '1#变频泵', 'pump');  -- 新ID可能不是121
```
**影响**：
- ❌ 所有依赖数据被级联删除（calculation_parameters、device_rated_params、optimization_history）
- ❌ 需要重新配置参数

#### 场景3：TRUNCATE后重建（高风险）
```sql
TRUNCATE TABLE dim_devices CASCADE;  -- 清空表并级联删除所有依赖数据
-- 重新导入数据，ID从1开始
```
**影响**：
- ❌ 所有依赖数据被级联删除
- ❌ 所有参数配置丢失

### 3.3 实际风险评估

| 场景 | 发生概率 | 影响范围 | 级联更新 | 数据丢失风险 |
|------|---------|---------|---------|------------|
| 手动修改ID | 极低 | 所有依赖表 | ✅ 自动更新 | 无 |
| 删除后重新插入 | 低 | 所有依赖表 | ❌ 级联删除 | 高 |
| TRUNCATE重建 | 中 | 所有依赖表 | ❌ 级联删除 | 极高 |
| UPSERT更新 | 高 | 无 | 不触发 | 无 |

**结论**：
- ✅ 正常的UPSERT操作不会导致ID变化
- ⚠️ 删除操作会导致参数丢失（级联删除）
- ⚠️ TRUNCATE操作会导致所有参数丢失
