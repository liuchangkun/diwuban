### P0 - 致命问题（必须立即修复）

#### 问题1：循环依赖指标的数组索引错误 ❌

**位置**：`app/services/calculation/orchestrator.py`, lines 1514-1538

**错误信息**：
```
IndexError: boolean index did not match indexed array along axis 0;
size of axis is 7200 but size of corresponding boolean axis is 3999/156
```

**根本原因**：
1. Line 1518: 验证失败时，`values = values[mask]` 过滤了 values 数组
2. Line 1537-1538: 调用 write_results 时，使用原始 timestamps，但 values 已被过滤
3. 结果：timestamps 长度 = 7200，values 长度 = 3999/156（被 mask 过滤后）
4. Line 998: write_results 方法中，`valid_timestamps = timestamps[valid_mask]` 尝试用长度不匹配的 mask 索引 timestamps

**错误代码**：
```python
# Line 1515: 验证（统一签名）
is_valid, mask, errors, warnings = self.validator.validate_ctx(member, values, ctx)
if not is_valid and mask is not None:
    logger.warning(f"循环依赖指标 {member} 验证失败: {errors}")
    values = values[mask]  # ❌ 过滤了 values 数组
# ...
if write_to_db:
    written = self.write_results(
        station_id=station_id,
        device_id=device_id,
        metric_key=member,
        timestamps=timestamps,  # ❌ 使用原始 timestamps
        values=values,  # ❌ 但 values 已被过滤
        quality_status=0,
        is_cyclic=True
    )
```

**正确的处理方式**（参考 lines 2042-2047）：
```python
# 当过滤后长度变化时，按mask对齐timestamps
write_ts = timestamps
try:
    if mask is not None and hasattr(mask, '__len__') and len(mask) == len(timestamps):
        if len(filtered_values) != len(timestamps):
            write_ts = timestamps[mask]  # ✅ 同步过滤 timestamps
except Exception:
    write_ts = timestamps
```

**修复方案**：
在 Line 1525（write_to_db 判断后）添加 timestamps 对齐逻辑：
```python
if write_to_db:
    write_start = time.time()
    # 添加：当过滤后长度变化时，按mask对齐timestamps
    write_ts = timestamps
    try:
        if mask is not None and hasattr(mask, '__len__') and len(mask) == len(timestamps):
            if len(values) != len(timestamps):
                write_ts = timestamps[mask]
    except Exception:
        write_ts = timestamps

    # 设备类型校验（循环组场景）
    dtype = self._get_device_type(station_id, device_id)
    if dtype and not self._metric_allowed_for_device(member, dtype):
        logger.info(f"skip write: metric={member} not allowed for device_type={dtype}")
    else:
        written = self.write_results(
            station_id=station_id,
            device_id=device_id,
            metric_key=member,
            timestamps=write_ts,  # ✅ 使用对齐后的 timestamps
            values=values,
            quality_status=0,
            is_cyclic=True
        )
```

**影响范围**：
- 所有循环依赖指标的计算和写入
- 当前项目中可能包括：pump_outlet_pressure, pump_inlet_pressure 等

**优先级**：🔴 P0 - 必须立即修复

#### 问题2：calculation_parameters 表的设计问题（误判） ✅

**初步判断**：❌ 错误
- 现象：所有21条记录的 `device_id` 和 `station_id` 都是 NULL
- 初步推断：无法为任何设备提供计算参数

**深度分析后的结论**：✅ 这是**正确的设计**
- **设计意图**：自适应SQL脚本故意设计为全局默认参数（device_id=NULL, station_id=NULL）
- **证据1**：`scripts/sql/adaptive/03_calculation_parameters.sql` 第20-21行注释明确说明
  ```sql
  -- ============================================
  -- 类型1：全局默认参数（station_id = NULL, device_id = NULL）
  -- ============================================
  ```
- **证据2**：计算引擎的 `load_parameters()` 方法（lines 712-728）**正确支持** NULL device_id 的全局参数
  ```python
  # 层级1：加载全局计算参数（最低优先级）
  query = """
      SELECT param_name, param_value, param_value_text, param_type
      FROM calculation_parameters
      WHERE device_id IS NULL
        AND station_id IS NULL
        AND method_id = %s
  """
  ```
- **证据3**：5层参数优先级系统设计合理
  1. 全局计算参数（device_id=NULL, station_id=NULL）← 当前使用
  2. 全局默认额定参数（global_default_rated_params）
  3. 设备额定参数（device_rated_params）
  4. 泵站级计算参数（station_id=X, device_id=NULL）
  5. 设备级计算参数（device_id=X）

**结论**：这不是问题，是正确的设计。参数查询逻辑工作正常。
