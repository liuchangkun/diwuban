### 1.2 无外键约束的表（❌ 风险）

#### 1.2.1 核心数据表（⚠️ 极高风险）

| 表名 | Schema | 列名 | 表类型 | 当前记录数 | 风险等级 | 影响说明 |

**详细分析**：
- **表类型**：TimescaleDB Hypertable（时序数据库超表）
- **分区策略**：按时间分区（每周一个chunk）
- **数据量**：515,355条记录（2025-05-31 18:00 - 19:59）
- **设备覆盖**：8个设备，1个泵站
- **外键状态**：❌ 无外键约束
- **孤立记录检查**：✅ 当前无孤立记录（所有device_id和station_id都有效）
- **风险**：如果dim_devices.id或dim_stations.id变化，这51万+记录不会自动更新，导致数据孤立

**为什么没有外键**：
- TimescaleDB的hypertable通常不支持外键约束（性能考虑）
- 分区表（chunks）无法直接添加外键
- 需要应用层保证数据一致性

## 三、风险评估

### 3.1 场景1：UPDATE dim_devices SET id = 新ID WHERE id = 旧ID

**有外键约束的表（16个）**：
- ✅ **自动更新**：所有16个表的 device_id 会自动从旧ID更新到新ID

## 四、根因分析

### 4.1 为什么之前的测试没有发现这些表？

**原因1：查询范围限制**
- 之前的查询只查询了 `public` schema 的外键约束
- 没有查询所有包含 `device_id` 或 `station_id` 列的表

**原因2：TimescaleDB特殊性**
- `fact_measurements` 是 TimescaleDB Hypertable
- Hypertable 通常不支持外键约束（性能考虑）
- 分区表（chunks）在 `_timescaledb_internal` schema 中

**原因3：视图和物化视图**
- 视图不需要外键约束（动态查询）
- 物化视图会定期刷新，ID变化后刷新时会自动更新

### 4.2 为什么 fact_measurements 没有外键约束？

**技术原因**：
1. **性能考虑**：fact_measurements 是核心时序数据表，每秒插入大量数据，外键约束会严重影响写入性能
2. **TimescaleDB限制**：Hypertable 不支持外键约束到普通表
3. **分区策略**：按时间分区的表难以维护外键约束

**设计决策**：
- 依赖应用层保证数据一致性
- 使用 UPSERT 策略确保 ID 稳定性
- 定期数据质量检查

## 五、建议和解决方案

### 5.1 短期建议（立即执行）

#### 建议1：为配置表添加外键约束

**目标表**：
- device_running_thresholds
- metric_quality_rules
- metric_rule_auto_baseline

**SQL脚本**：
```sql
-- 为 device_running_thresholds 添加外键
ALTER TABLE device_running_thresholds
ADD CONSTRAINT device_running_thresholds_device_id_fkey
FOREIGN KEY (device_id) REFERENCES dim_devices(id)
ON UPDATE CASCADE ON DELETE CASCADE;

-- 为 metric_quality_rules 添加外键
ALTER TABLE metric_quality_rules
ADD CONSTRAINT metric_quality_rules_device_id_fkey
FOREIGN KEY (device_id) REFERENCES dim_devices(id)
ON UPDATE CASCADE ON DELETE CASCADE;

ALTER TABLE metric_quality_rules
ADD CONSTRAINT metric_quality_rules_station_id_fkey
FOREIGN KEY (station_id) REFERENCES dim_stations(id)
ON UPDATE CASCADE ON DELETE CASCADE;

-- 为 metric_rule_auto_baseline 添加外键
ALTER TABLE metric_rule_auto_baseline
ADD CONSTRAINT metric_rule_auto_baseline_device_id_fkey
FOREIGN KEY (device_id) REFERENCES dim_devices(id)
ON UPDATE CASCADE ON DELETE CASCADE;

ALTER TABLE metric_rule_auto_baseline
ADD CONSTRAINT metric_rule_auto_baseline_station_id_fkey
FOREIGN KEY (station_id) REFERENCES dim_stations(id)
ON UPDATE CASCADE ON DELETE CASCADE;
```

**预期效果**：
- ✅ 配置表的 device_id 和 station_id 会自动跟随维度表变化
- ✅ 删除设备时配置会自动清理
- ✅ 防止配置表出现孤立记录

#### 建议2：增强数据一致性检查

**创建定期检查脚本**：
```sql
-- 检查 fact_measurements 中的孤立记录
SELECT 
    '孤立的device_id' as 检查项,
    COUNT(DISTINCT fm.device_id) as 孤立ID数量,
    array_agg(DISTINCT fm.device_id) as 孤立ID列表
FROM fact_measurements fm
LEFT JOIN dim_devices d ON d.id = fm.device_id
WHERE d.id IS NULL;

-- 检查 device_running_thresholds 中的孤立记录
SELECT 
    '孤立的device_id' as 检查项,
    COUNT(*) as 孤立记录数,
    array_agg(device_id) as 孤立ID列表
FROM device_running_thresholds drt
LEFT JOIN dim_devices d ON d.id = drt.device_id
WHERE d.id IS NULL;
```

### 5.2 中期建议（1-3个月）

#### 建议3：实施应用层ID同步机制

**对于无法添加外键的表（如 fact_measurements）**：

**方案A：触发器同步**
```sql
-- 创建触发器函数
CREATE OR REPLACE FUNCTION sync_fact_measurements_device_id()
RETURNS TRIGGER AS $$
BEGIN
    -- 当 dim_devices.id 更新时，同步 fact_measurements
    UPDATE fact_measurements
    SET device_id = NEW.id
    WHERE device_id = OLD.id;
    
    RETURN NEW;
```

```sql
CREATE OR REPLACE FUNCTION sync_fact_measurements_device_id_batch()
RETURNS TRIGGER AS $$
DECLARE
    batch_size INT := 10000;
    affected_rows INT;
BEGIN
    LOOP
        UPDATE fact_measurements
        SET device_id = NEW.id
        WHERE device_id = OLD.id
        LIMIT batch_size;

        GET DIAGNOSTICS affected_rows = ROW_COUNT;
        EXIT WHEN affected_rows = 0;

        -- 提交批次，释放锁
        PERFORM pg_sleep(0.1);
    END LOOP;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```
