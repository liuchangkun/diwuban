## 🔍 问题分析

### 问题：optimization_history 恢复失败

**根本原因**：
1. `optimization_history` 包含历史设备ID（device_id=153）
2. `dim_devices` 在 prepare_dim 阶段1被重建，新的设备ID不包含153
3. 外键约束 `optimization_history_device_id_fkey` 阻止了恢复

**设计冲突**：
- **初衷**：将 optimization_history 归类为"需要备份导入"的A类手动配置表，因为它包含RLS状态
- **现实**：optimization_history 包含历史设备ID，与"配置数据跟随ID变化"的原则冲突

**两种解决方案**：

#### 方案1：将 optimization_history 从备份机制中移除（推荐）

**理由**：
- optimization_history 本质上是历史数据表，记录了过去的优化状态
- 历史数据应该保留历史ID，不应该跟随维度表ID变化
- RLS状态虽然重要，但可以重新计算

**实施**：
1. 从 `tables_to_backup` 列表中移除 optimization_history
2. 从 `manual_config_tables` 列表中移除 optimization_history
3. 从清空表逻辑中移除 optimization_history（让它在清空 dim_devices 时自动级联删除）
4. 更新文档说明

**优点**：
- 符合"历史数据保留历史ID"的原则
- 避免外键约束冲突
- 简化备份和恢复逻辑

**缺点**：
- 每次 prepare_dim 后需要重新计算RLS状态
- 丢失历史优化记录

#### 方案2：修改 optimization_history 的外键约束（不推荐）

**理由**：
- 将外键约束改为 `ON DELETE SET NULL` 或 `ON DELETE CASCADE`
- 允许恢复时忽略不存在的设备ID

**实施**：
1. 修改外键约束为 `ON DELETE SET NULL`
2. 在恢复时跳过外键约束检查

**优点**：
- 保留历史优化记录

**缺点**：
- 违反"配置数据跟随ID变化"的原则
- 可能导致数据不一致
- 增加复杂性
